# Системные правила разработки проекта

## 1. Язык общения и документации

### Обязательные требования
- Все диалоги, объяснения архитектуры и ответы в чате ведутся строго на русском языке
- Комментарии в коде на русском языке
- Логика разработки должна быть абсолютно понятна

### Работа с документацией
- **ЗАПРЕЩЕНО** писать и обновлять документацию после каждого изменения
- По итогам работы выдавать только краткую выжимку прямо в чате
- Полноценную документацию создавать или обновлять **исключительно по прямой просьбе пользователя**
- Не засорять проект избыточной документацией

## 2. Архитектура и модульность

### Принципы проектирования
- Проектировать максимально масштабируемую систему, удобную для рефакторинга и добавления новых фичей
- **Железное правило**: один независимый модуль или логический блок = один отдельный файл
- **ЗАПРЕЩЕНО** раздувать файлы
- Каждая функция должна быть масштабируемой
- Модульная структура с чёткой ответственностью каждого компонента

### Требования к структуре
- Красивая и удобная настройка проекта
- Логическое разделение функциональности
- Избегать монолитных файлов
- Строго следовать принципу единственной ответственности (Single Responsibility Principle)
- Отдельная реализация для каждого модуля в своём файле

## 3. Тесты, ошибки и рефакторинг (Zero Tolerance Policy)

### Критически важно — политика нулевой терпимости к ошибкам
- **НИКОГДА не пропускать ошибки** во время spec-тестов
- Словил ошибку — **сразу исправляешь до победного**
- Если вылезла баг из старого кода — **останавливаешься и чинишь её идеально**
- **НЕ ИСПОЛЬЗОВАТЬ костыли** — только правильные решения
- **НЕ ОСТАВЛЯТЬ ошибки "на потом"** — каждая ошибка исправляется немедленно

### Подход к исправлению
- Если ошибка возникла на этапе Task — исправить её немедленно
- Если ошибка из прошлого этапа проявляется на текущем — исправить её, независимо от того, на каком этапе находимся
- Отслеживать все ошибки на протяжении всех этапов
- Не игнорировать ошибки под предлогом "это другой этап"
- Продолжать исправлять до полного устранения проблемы
- Проверять, что исправление не создало новых проблем

### Рефакторинг и архитектурная чистота
- Если видишь, что механику лучше полностью переписать для более правильной работы всей системы — **смело переписывай**
- **Архитектурная чистота всегда в приоритете**
- Не бояться масштабных изменений ради улучшения архитектуры
- Качество системы важнее скорости разработки

## 4. Python и виртуальное окружение

### Обязательные требования
- **ВСЕ Python скрипты выполняются ТОЛЬКО через виртуальное окружение**
- Перед выполнением любого Python кода активировать виртуальное окружение
- Установка зависимостей только в виртуальное окружение
- Не использовать глобальный Python интерпретатор для проекта

### Команды для работы
- Активация виртуального окружения (Windows): `venv\Scripts\activate`
- Активация виртуального окружения (Linux/Mac): `source venv/bin/activate`
- Выполнение скриптов: всегда через активированное окружение
- Установка пакетов: `pip install <package>` только после активации venv

### Структура проекта
- Виртуальное окружение в папке `venv/` (добавить в .gitignore)
- Файл `requirements.txt` для управления зависимостями
- Обновлять `requirements.txt` при добавлении новых зависимостей

## 5. Качество кода

### Стандарты написания
- Чистый, читаемый код
- Понятные имена переменных и функций на русском языке (где применимо) или английском (для технических терминов)
- Комментарии для сложной логики на русском языке
- Следование best practices для используемого языка/фреймворка
- Код должен быть самодокументируемым

### Приоритеты
1. Корректность работы
2. Архитектурная чистота
3. Читаемость и поддерживаемость
4. Производительность (оптимизировать только при необходимости)
