# Документ требований: Рефакторинг архитектуры Telegram-бота с PostgreSQL и синхронизацией

## Введение

Данный документ описывает требования к рефакторингу архитектуры Telegram-бота для перехода от прямых запросов к Google Sheets на архитектуру с PostgreSQL в качестве основного хранилища данных и периодической синхронизацией.

### Текущая проблема

Существующая архитектура выполняет запрос к Google Sheets API при каждом вводе кодового слова пользователем. Это приводит к:
- Медленной работе бота (задержки ответа)
- Быстрому достижению лимитов Google Sheets API при наплыве пользователей
- Невозможности масштабирования системы

### Целевое решение

Google Sheets остается панелью управления для команды (добавление новых призов, просмотр данных победителей). Вся нагрузка от бота переносится на PostgreSQL. Синхронизация данных из Google Sheets в PostgreSQL выполняется автоматически по таймеру раз в минуту.

## Глоссарий

- **Bot**: Telegram-бот, обрабатывающий запросы пользователей
- **Sync_Service**: Сервис синхронизации данных из Google Sheets в PostgreSQL
- **Database**: База данных PostgreSQL
- **Google_Sheets**: Таблица Google Sheets, используемая как панель управления
- **Prize_Record**: Запись о призе в базе данных
- **Code_Word**: Кодовое слово для активации приза
- **Sheet_Name**: Название листа (worksheet) в Google Sheets
- **Telegram_ID**: Уникальный идентификатор пользователя Telegram
- **Prize_Type**: Тип приза (digital или physical)
- **Delivery_Data**: Данные доставки для физических призов
- **Upsert**: Операция вставки или обновления записи (insert or update)

## Требования

### Требование 1: Структура базы данных PostgreSQL

**User Story:** Как разработчик, я хочу иметь единую таблицу для хранения всех призов, чтобы обеспечить быструю проверку промокодов.

#### Критерии приемки

1. THE Database SHALL содержать таблицу prizes с следующими полями:
   - id (Primary Key, автоинкремент)
   - telegram_id (BIGINT, NOT NULL)
   - prize_type (VARCHAR, NOT NULL, значения: 'digital' или 'physical')
   - promo_code (VARCHAR, NULL, для digital призов)
   - instructions (TEXT, NULL, для digital призов)
   - last_name (VARCHAR, NULL, для physical призов)
   - first_name (VARCHAR, NULL, для physical призов)
   - patronymic (VARCHAR, NULL, для physical призов)
   - city (VARCHAR, NULL, для physical призов)
   - street (VARCHAR, NULL, для physical призов)
   - house (VARCHAR, NULL, для physical призов)
   - apartment (VARCHAR, NULL, для physical призов)
   - phone (VARCHAR, NULL, для physical призов)
   - comment (TEXT, NULL, для physical призов)
   - sheet_name (VARCHAR, NOT NULL, название листа-источника)
   - code_word (VARCHAR, NOT NULL, кодовое слово)
   - row_id (INTEGER, NOT NULL, номер строки в Google Sheets)
   - created_at (TIMESTAMP, NOT NULL, время создания записи)
   - updated_at (TIMESTAMP, NOT NULL, время последнего обновления)

2. THE Database SHALL создавать составной уникальный индекс на поля (telegram_id, code_word) для предотвращения дублирования

3. THE Database SHALL создавать индекс на поле code_word для быстрого поиска по кодовому слову

4. THE Database SHALL создавать индекс на поле sheet_name для быстрого поиска записей по листу

### Требование 2: Сервис синхронизации данных

**User Story:** Как администратор системы, я хочу автоматически синхронизировать данные из Google Sheets в PostgreSQL, чтобы бот работал с актуальными данными без прямых запросов к Google API.

#### Критерии приемки

1. THE Sync_Service SHALL запускаться автоматически каждые 60 секунд

2. WHEN Sync_Service запускается, THE Sync_Service SHALL получать список всех листов (worksheets) из Google_Sheets через API

3. FOR каждого листа в списке, THE Sync_Service SHALL читать все строки данных начиная со второй строки (первая строка - заголовки)

4. FOR каждой строки данных, THE Sync_Service SHALL выполнять операцию upsert в таблицу prizes:
   - IF запись с таким (telegram_id, code_word) существует, THEN THE Sync_Service SHALL обновить все поля кроме id и created_at
   - IF запись с таким (telegram_id, code_word) не существует, THEN THE Sync_Service SHALL создать новую запись

5. WHEN Sync_Service обрабатывает строку, THE Sync_Service SHALL заполнять поле sheet_name названием текущего листа

6. WHEN Sync_Service обрабатывает строку, THE Sync_Service SHALL заполнять поле code_word названием текущего листа (кодовое слово = название листа)

7. WHEN Sync_Service обрабатывает строку, THE Sync_Service SHALL заполнять поле row_id номером строки в Google Sheets

8. IF во время синхронизации происходит ошибка API Google, THEN THE Sync_Service SHALL логировать ошибку и продолжить работу со следующим листом

9. WHEN синхронизация завершается, THE Sync_Service SHALL логировать статистику: количество обработанных листов, добавленных записей, обновленных записей, ошибок

10. THE Sync_Service SHALL использовать retry-логику с экспоненциальной задержкой для обработки временных сбоев Google Sheets API (максимум 3 попытки)

### Требование 3: Проверка промокода через PostgreSQL

**User Story:** Как пользователь бота, я хочу быстро получать ответ при вводе кодового слова, чтобы не ждать долго.

#### Критерии приемки

1. WHEN пользователь отправляет кодовое слово, THE Bot SHALL искать Prize_Record в Database по полям (telegram_id пользователя, code_word)

2. THE Bot SHALL НЕ выполнять запросы к Google_Sheets для проверки промокода

3. IF Prize_Record найдена в Database, THEN THE Bot SHALL отправить пользователю информацию о призе

4. IF Prize_Record не найдена в Database, THEN THE Bot SHALL отправить пользователю сообщение о том, что промокод не найден

5. WHEN Prize_Record найдена, THE Bot SHALL определить тип приза из поля prize_type

6. IF prize_type равен 'digital', THEN THE Bot SHALL отправить пользователю promo_code и instructions

7. IF prize_type равен 'physical', THEN THE Bot SHALL запустить процесс сбора данных доставки

8. THE Bot SHALL выполнять поиск в Database с таймаутом не более 500 миллисекунд

### Требование 4: Запись данных победителя в Google Sheets

**User Story:** Как администратор, я хочу видеть данные победителей в Google Sheets, чтобы управлять доставкой призов.

#### Критерии приемки

1. WHEN пользователь завершает ввод данных доставки, THE Bot SHALL записать Delivery_Data обратно в Google_Sheets

2. THE Bot SHALL использовать значение sheet_name из Prize_Record для определения целевого листа в Google_Sheets

3. THE Bot SHALL использовать значение row_id из Prize_Record для определения номера строки в Google_Sheets

4. THE Bot SHALL обновить следующие колонки в Google_Sheets:
   - Колонка E (индекс 4): last_name
   - Колонка F (индекс 5): first_name
   - Колонка G (индекс 6): patronymic
   - Колонка H (индекс 7): city
   - Колонка I (индекс 8): street
   - Колонка J (индекс 9): house
   - Колонка K (индекс 10): apartment
   - Колонка L (индекс 11): phone
   - Колонка M (индекс 12): comment

5. THE Bot SHALL использовать batch update API для эффективной записи всех полей одним запросом

6. IF запись в Google_Sheets завершается ошибкой, THEN THE Bot SHALL повторить попытку до 3 раз с экспоненциальной задержкой

7. IF все попытки записи неуспешны, THEN THE Bot SHALL логировать ошибку и уведомить пользователя о технической проблеме

8. WHEN запись в Google_Sheets успешна, THE Bot SHALL также обновить соответствующие поля в Database для синхронизации данных

### Требование 5: Модульная архитектура

**User Story:** Как разработчик, я хочу иметь чистую модульную архитектуру, чтобы легко поддерживать и расширять систему.

#### Критерии приемки

1. THE система SHALL разделять функциональность на независимые модули, где каждый модуль находится в отдельном файле

2. THE Sync_Service SHALL быть реализован в отдельном модуле sync_service.py

3. THE Database модель Prize_Record SHALL быть определена в отдельном файле models/prize.py

4. THE Database репозиторий для работы с Prize_Record SHALL быть реализован в отдельном файле repositories/prize_repository.py

5. THE конфигурация синхронизации SHALL быть добавлена в config.py как отдельный класс SyncConfig

6. THE запуск Sync_Service SHALL быть реализован в отдельном скрипте sync_worker.py

7. THE каждый модуль SHALL иметь единственную ответственность согласно принципу Single Responsibility Principle

8. THE все модули SHALL иметь комментарии на русском языке, объясняющие их назначение

### Требование 6: Управление зависимостями и окружением

**User Story:** Как разработчик, я хочу использовать виртуальное окружение Python, чтобы изолировать зависимости проекта.

#### Критерии приемки

1. THE все Python скрипты SHALL выполняться только через активированное виртуальное окружение

2. THE файл requirements.txt SHALL содержать все необходимые зависимости с указанием версий

3. THE новые зависимости для синхронизации SHALL быть добавлены в requirements.txt:
   - APScheduler>=3.10.4 (для планирования задач)

4. THE документация SHALL содержать инструкции по активации виртуального окружения для Windows и Linux/Mac

### Требование 7: Логирование и мониторинг

**User Story:** Как администратор системы, я хочу видеть подробные логи работы синхронизации, чтобы отслеживать проблемы и производительность.

#### Критерии приемки

1. THE Sync_Service SHALL логировать начало каждого цикла синхронизации с временной меткой

2. THE Sync_Service SHALL логировать завершение каждого цикла синхронизации со статистикой:
   - Количество обработанных листов
   - Количество добавленных записей
   - Количество обновленных записей
   - Количество ошибок
   - Время выполнения синхронизации

3. WHEN происходит ошибка Google Sheets API, THE Sync_Service SHALL логировать детали ошибки включая:
   - Тип ошибки
   - Название листа
   - Номер строки (если применимо)
   - Текст ошибки

4. THE Sync_Service SHALL использовать structlog для структурированного логирования

5. THE логи SHALL содержать уровни: INFO для нормальной работы, WARNING для восстановимых ошибок, ERROR для критических ошибок

6. WHEN Bot выполняет поиск в Database, THE Bot SHALL логировать время выполнения запроса

7. IF время выполнения запроса превышает 500 миллисекунд, THEN THE Bot SHALL логировать предупреждение о медленном запросе

### Требование 8: Обработка ошибок и устойчивость

**User Story:** Как пользователь системы, я хочу чтобы система продолжала работать даже при временных сбоях, чтобы получать стабильный сервис.

#### Критерии приемки

1. IF Google_Sheets API недоступен во время синхронизации, THEN THE Sync_Service SHALL логировать ошибку и продолжить работу в следующем цикле

2. IF Database недоступна во время синхронизации, THEN THE Sync_Service SHALL логировать критическую ошибку и повторить попытку в следующем цикле

3. IF Bot не может подключиться к Database, THEN THE Bot SHALL отправить пользователю сообщение о временной недоступности сервиса

4. THE Sync_Service SHALL использовать connection pooling для эффективного управления подключениями к Database

5. THE Sync_Service SHALL закрывать все подключения к Database при завершении работы (graceful shutdown)

6. IF во время upsert операции происходит конфликт уникального индекса, THEN THE Sync_Service SHALL выполнить update существующей записи

7. THE система SHALL использовать транзакции для обеспечения консистентности данных при batch операциях

### Требование 9: Производительность и масштабируемость

**User Story:** Как администратор системы, я хочу чтобы система эффективно обрабатывала большое количество пользователей, чтобы избежать проблем при наплыве трафика.

#### Критерии приемки

1. THE Sync_Service SHALL обрабатывать синхронизацию одного листа с 1000 записями за время не более 30 секунд

2. THE Bot SHALL выполнять поиск Prize_Record в Database за время не более 100 миллисекунд в 95% случаев

3. THE Database SHALL использовать индексы для оптимизации запросов поиска по (telegram_id, code_word)

4. THE Sync_Service SHALL использовать batch insert/update операции для минимизации количества запросов к Database

5. THE Sync_Service SHALL обрабатывать листы параллельно (если возможно) для ускорения синхронизации

6. THE система SHALL поддерживать одновременную работу нескольких экземпляров Bot без конфликтов

7. THE Database connection pool SHALL иметь минимум 5 и максимум 20 подключений для оптимального использования ресурсов

### Требование 10: Обратная совместимость и миграция

**User Story:** Как разработчик, я хочу плавно перейти на новую архитектуру, чтобы не нарушить работу существующей системы.

#### Критерии приемки

1. THE новая таблица prizes SHALL быть создана через Alembic миграцию

2. THE миграция SHALL быть идемпотентной (можно запускать многократно без ошибок)

3. THE существующий код Bot SHALL продолжать работать до завершения первой синхронизации

4. THE GoogleSheetsService SHALL быть сохранен для функции записи данных победителя

5. THE новый PrizeRepository SHALL предоставлять тот же интерфейс, что и старый GoogleSheetsService для поиска призов

6. THE система SHALL поддерживать откат на старую архитектуру через feature flag в конфигурации

7. WHEN feature flag use_postgres установлен в False, THEN THE Bot SHALL использовать старую логику с прямыми запросами к Google_Sheets

8. WHEN feature flag use_postgres установлен в True, THEN THE Bot SHALL использовать новую логику с PostgreSQL

### Требование 11: Тестирование и качество кода

**User Story:** Как разработчик, я хочу иметь автоматические тесты, чтобы гарантировать корректность работы системы.

#### Критерии приемки

1. THE PrizeRepository SHALL иметь unit тесты для всех публичных методов

2. THE Sync_Service SHALL иметь unit тесты с mock объектами для Google_Sheets и Database

3. THE система SHALL иметь integration тесты для проверки полного цикла синхронизации

4. THE тесты SHALL использовать pytest и pytest-asyncio для асинхронного кода

5. THE тесты SHALL использовать Hypothesis для property-based тестирования операций upsert

6. FOR операции upsert, THE тесты SHALL проверять свойство идемпотентности: выполнение upsert дважды с одинаковыми данными дает тот же результат

7. THE тесты SHALL проверять корректность обработки ошибок и retry логики

8. THE код SHALL соответствовать стандартам PEP 8 для Python

9. THE все функции и классы SHALL иметь docstrings на русском языке

10. THE критические участки кода SHALL иметь inline комментарии на русском языке для объяснения сложной логики
