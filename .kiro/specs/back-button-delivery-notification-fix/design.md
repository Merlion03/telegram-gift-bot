# Bugfix Design: Исправление кнопки "Назад" в процессе получения физического приза

## Overview

Баг возникает когда пользователь, уже заполнивший форму доставки для физического приза, вводит кодовое слово повторно и нажимает кнопку "Назад". Вместо простого возврата в главное меню система ошибочно отправляет уведомления о подтверждении доставки ("Данные отправлены!" и сообщение о готовности к отправке).

Корневая причина: кнопка "Назад" использует callback_data `confirm_delivery:{prize_id}`, который обрабатывается методом `handle_confirm_delivery_callback`. Этот метод был изначально создан для подтверждения отправки данных, а не для возврата в меню.

Стратегия исправления: создать отдельный callback handler для кнопки "Назад", который будет просто удалять inline-клавиатуру и показывать главное меню без отправки уведомлений.

## Glossary

- **Bug_Condition (C)**: Условие, при котором проявляется баг - когда пользователь нажимает кнопку "Назад" после повторного ввода кодового слова для уже заполненной формы доставки
- **Property (P)**: Желаемое поведение при нажатии кнопки "Назад" - возврат в главное меню без отправки уведомлений
- **Preservation**: Существующее поведение кнопки "Изменить данные" и процесса первичного заполнения формы, которое должно остаться неизменным
- **handle_confirm_delivery_callback**: Метод в `telegram-bot/handlers/prize_flow_handler.py`, который обрабатывает callback от кнопки "Назад" и ошибочно отправляет уведомления
- **get_delivery_actions_keyboard**: Функция в `telegram-bot/keyboards/reply_keyboards.py`, которая создаёт inline-клавиатуру с кнопками "Назад" и "Изменить данные"
- **notification_service.send_delivery_notifications**: Метод, который отправляет уведомления о подтверждении доставки (вызывается ошибочно при нажатии "Назад")
- **is_delivery_filled**: Флаг, определяющий, заполнена ли форма доставки для данного приза

## Bug Details

### Bug Condition

Баг проявляется когда пользователь уже заполнил форму доставки для физического приза, вводит кодовое слово повторно, и нажимает кнопку "Назад". Метод `handle_confirm_delivery_callback` обрабатывает этот callback и вызывает `notification_service.send_delivery_notifications`, что приводит к отправке уведомлений вместо простого возврата в меню.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type CallbackQuery
  OUTPUT: boolean
  
  RETURN input.data.startswith("confirm_delivery:")
         AND user_clicked_back_button
         AND delivery_form_already_filled
         AND NOT user_wants_to_confirm_delivery
END FUNCTION
```

### Examples

- **Пример 1**: Пользователь заполнил форму доставки для приза с prize_id=123. Через некоторое время он вводит то же кодовое слово снова. Система показывает сообщение "Вы уже заполнили данные для получения приза" с кнопками "Назад" и "Изменить данные". Пользователь нажимает "Назад", ожидая вернуться в главное меню. Вместо этого он получает всплывающее уведомление "Данные отправлены!" и сообщение "Отлично, всё готово к отправке!".

- **Пример 2**: Пользователь случайно ввёл кодовое слово повторно после заполнения формы. Видит кнопки "Назад" и "Изменить данные". Нажимает "Назад", чтобы просто закрыть это сообщение и вернуться к главному меню. Получает уведомления о подтверждении, хотя ничего не подтверждал.

- **Пример 3**: Пользователь хочет проверить статус своего приза, вводит кодовое слово. Видит, что данные уже заполнены. Нажимает "Назад", чтобы вернуться в меню. Система отправляет уведомления о подтверждении доставки, создавая путаницу.

- **Edge case**: Пользователь быстро нажимает кнопку "Назад" несколько раз подряд - каждое нажатие должно обрабатываться корректно без дублирования уведомлений (хотя в идеале после первого нажатия кнопка должна исчезнуть).

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Кнопка "Изменить данные" (WebApp) должна продолжать открывать форму доставки для редактирования
- Первичное заполнение формы доставки через WebApp должно работать без изменений
- Отправка данных через WebApp должна продолжать вызывать уведомления о подтверждении
- Процесс получения цифровых призов должен работать без изменений
- Все другие состояния процесса получения приза должны работать без изменений

**Scope:**
Все взаимодействия, которые НЕ связаны с нажатием кнопки "Назад" в контексте уже заполненной формы доставки, должны быть полностью не затронуты этим исправлением. Это включает:
- Нажатие кнопки "Изменить данные" (WebApp)
- Первичное заполнение формы доставки
- Отправку данных через WebApp
- Получение цифровых призов
- Любые другие callback handlers в системе

## Hypothesized Root Cause

На основе анализа кода, наиболее вероятные причины бага:

1. **Неправильное использование callback_data**: Кнопка "Назад" использует `callback_data=f"confirm_delivery:{prize_id}"`, который семантически означает "подтвердить доставку", а не "вернуться назад". Это приводит к тому, что handler `handle_confirm_delivery_callback` интерпретирует нажатие как подтверждение и отправляет уведомления.

2. **Отсутствие отдельного handler для возврата**: В системе нет отдельного callback handler для действия "вернуться в меню". Кнопка "Назад" переиспользует существующий handler для подтверждения доставки.

3. **Семантическая путаница в коде**: Метод `handle_confirm_delivery_callback` имеет docstring "Обрабатывает нажатие на кнопку 'Получить приз' для уже заполненной формы", но фактически обрабатывает кнопку "Назад". Это указывает на то, что изначально кнопка могла называться "Получить приз", а затем была переименована в "Назад" без изменения логики.

4. **Отсутствие проверки намерения пользователя**: Handler не проверяет, действительно ли пользователь хочет подтвердить доставку или просто вернуться в меню. Он безусловно вызывает `send_delivery_notifications`.

## Correctness Properties

Property 1: Bug Condition - Кнопка "Назад" возвращает в меню без уведомлений

_For any_ callback input где пользователь нажимает кнопку "Назад" после повторного ввода кодового слова для уже заполненной формы доставки, исправленная функция SHALL удалить inline-клавиатуру, показать главное меню и НЕ отправлять никаких уведомлений о подтверждении доставки.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5**

Property 2: Preservation - Поведение кнопки "Изменить данные" и других процессов

_For any_ взаимодействие, которое НЕ является нажатием кнопки "Назад" (нажатие "Изменить данные", первичное заполнение формы, отправка через WebApp, получение цифровых призов), исправленный код SHALL производить точно такой же результат, как и оригинальный код, сохраняя всю существующую функциональность.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4, 3.5**

## Fix Implementation

### Changes Required

Предполагая, что наш анализ корневой причины верен:

**File**: `telegram-bot/keyboards/reply_keyboards.py`

**Function**: `get_delivery_actions_keyboard`

**Specific Changes**:
1. **Изменить callback_data для кнопки "Назад"**: Заменить `callback_data=f"confirm_delivery:{prize_id}"` на `callback_data="back_to_menu"` или `callback_data=f"back_to_menu:{prize_id}"` (если нужен prize_id для логирования)
   - Это разделит семантику "подтвердить доставку" и "вернуться в меню"
   - Позволит создать отдельный handler для каждого действия

**File**: `telegram-bot/handlers/prize_flow_handler.py`

**New Method**: `handle_back_to_menu_callback`

**Specific Changes**:
2. **Создать новый метод для обработки кнопки "Назад"**:
   - Метод должен принимать `callback: CallbackQuery`, `state: FSMContext`, опционально `prize_id: int` и `session_id: Optional[int]`
   - Удалить inline-клавиатуру из сообщения (используя `callback.message.edit_reply_markup(reply_markup=None)`)
   - Отправить главное меню (используя `callback.message.answer` с `get_main_menu_keyboard()`)
   - Вызвать `callback.answer()` БЕЗ текста (или с пустой строкой) - это закроет callback без всплывающего уведомления
   - Сбросить FSM состояние (если необходимо)
   - Залогировать действие для отладки

3. **Обновить docstring метода `handle_confirm_delivery_callback`**: Уточнить, что этот метод больше не обрабатывает кнопку "Назад", а используется только для подтверждения доставки через другие механизмы (если такие есть, иначе метод может стать неиспользуемым)

**File**: `telegram-bot/main.py`

**Function**: Регистрация callback handlers

**Specific Changes**:
4. **Зарегистрировать новый callback handler**:
   - Добавить wrapper функцию `back_to_menu_callback_wrapper`
   - Зарегистрировать handler для `F.data.startswith("back_to_menu:")` или `F.data == "back_to_menu"`
   - Разместить регистрацию рядом с другими callback handlers для Prize Flow

5. **Опционально: удалить старый handler `confirm_delivery_callback_wrapper`**: Если после изменений метод `handle_confirm_delivery_callback` больше не используется, можно удалить его регистрацию. Однако, если есть другие места, где он используется, оставить его.

## Testing Strategy

### Validation Approach

Стратегия тестирования следует двухфазному подходу: сначала продемонстрировать баг на неисправленном коде (exploratory testing), затем проверить, что исправление работает корректно и сохраняет существующее поведение (fix checking и preservation checking).

### Exploratory Bug Condition Checking

**Goal**: Продемонстрировать баг ДО внедрения исправления. Подтвердить или опровергнуть анализ корневой причины. Если опровергнем, нужно будет пересмотреть гипотезу.

**Test Plan**: Написать тесты, которые симулируют нажатие кнопки "Назад" в контексте уже заполненной формы доставки. Запустить эти тесты на НЕИСПРАВЛЕННОМ коде, чтобы наблюдать ошибочное поведение (отправку уведомлений).

**Test Cases**:
1. **Тест нажатия кнопки "Назад"**: Симулировать callback с `data="confirm_delivery:123"` от пользователя, у которого форма доставки уже заполнена. Проверить, что вызывается `notification_service.send_delivery_notifications` (будет fail на неисправленном коде - это ожидаемо, мы хотим увидеть баг)
2. **Тест всплывающего уведомления**: Проверить, что `callback.answer` вызывается с текстом "Данные отправлены!" (будет fail на неисправленном коде)
3. **Тест отправки сообщения о готовности**: Проверить, что отправляется сообщение с текстом "Отлично, всё готово к отправке!" (будет fail на неисправленном коде)
4. **Тест повторного нажатия**: Симулировать быстрое двойное нажатие кнопки "Назад" и проверить, что уведомления отправляются дважды (может fail на неисправленном коде)

**Expected Counterexamples**:
- Метод `send_delivery_notifications` вызывается при нажатии "Назад"
- Callback answer содержит текст "Данные отправлены!"
- Отправляется сообщение о готовности к отправке
- Возможные причины: неправильный callback_data, отсутствие отдельного handler, семантическая путаница

### Fix Checking

**Goal**: Проверить, что для всех входных данных, где выполняется условие бага, исправленная функция производит ожидаемое поведение.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := handle_back_to_menu_callback_fixed(input)
  ASSERT expectedBehavior(result)
END FOR
```

**Expected Behavior:**
- Inline-клавиатура удалена из сообщения
- Главное меню отправлено пользователю
- Callback answer вызван БЕЗ текста (или с пустой строкой)
- Метод `send_delivery_notifications` НЕ вызван
- FSM состояние сброшено (если необходимо)

### Preservation Checking

**Goal**: Проверить, что для всех входных данных, где условие бага НЕ выполняется, исправленная функция производит тот же результат, что и оригинальная функция.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT original_behavior(input) = fixed_behavior(input)
END FOR
```

**Testing Approach**: Property-based testing рекомендуется для preservation checking, потому что:
- Автоматически генерирует множество тестовых случаев по всему входному домену
- Ловит edge cases, которые могут быть пропущены в ручных unit тестах
- Предоставляет сильные гарантии, что поведение не изменилось для всех не-багованных входов

**Test Plan**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для кнопки "Изменить данные" и других взаимодействий, затем написать property-based тесты, фиксирующие это поведение.

**Test Cases**:
1. **Preservation Test: Кнопка "Изменить данные"**: Наблюдать, что нажатие кнопки "Изменить данные" открывает WebApp форму на неисправленном коде. Написать тест, проверяющий, что это поведение сохраняется после исправления.
2. **Preservation Test: Первичное заполнение формы**: Наблюдать, что при первом вводе кодового слова для физического приза (когда форма НЕ заполнена) показывается WebApp форма. Написать тест, проверяющий сохранение этого поведения.
3. **Preservation Test: Отправка данных через WebApp**: Наблюдать, что при отправке данных через WebApp вызываются уведомления о подтверждении. Написать тест, проверяющий сохранение этого поведения.
4. **Preservation Test: Цифровые призы**: Проверить, что процесс получения цифровых призов работает идентично до и после исправления.

### Unit Tests

- Тест создания клавиатуры `get_delivery_actions_keyboard` с новым callback_data для кнопки "Назад"
- Тест метода `handle_back_to_menu_callback`: проверка удаления клавиатуры, отправки главного меню, вызова callback.answer без текста
- Тест, что `send_delivery_notifications` НЕ вызывается при нажатии "Назад"
- Тест edge case: быстрое двойное нажатие кнопки "Назад" не должно вызывать ошибок
- Тест логирования: проверить, что действие "возврат в меню" логируется корректно

### Property-Based Tests

- Генерировать случайные состояния пользователя (заполнена форма / не заполнена) и проверять, что кнопка "Назад" всегда возвращает в меню без уведомлений
- Генерировать случайные prize_id и проверять, что callback обрабатывается корректно для всех значений
- Генерировать случайные последовательности действий пользователя и проверять, что кнопка "Изменить данные" всегда открывает WebApp форму
- Тестировать, что все не-"Назад" взаимодействия продолжают работать идентично на многих сценариях

### Integration Tests

- Полный флоу: пользователь заполняет форму, вводит кодовое слово снова, нажимает "Назад", проверяет, что вернулся в главное меню без уведомлений
- Полный флоу: пользователь заполняет форму, вводит кодовое слово снова, нажимает "Изменить данные", проверяет, что открылась WebApp форма
- Полный флоу: пользователь впервые вводит кодовое слово для физического приза, проверяет, что показывается WebApp форма
- Тест переключения контекстов: пользователь переходит между разными состояниями Prize Flow и проверяет, что кнопка "Назад" работает корректно в каждом контексте
