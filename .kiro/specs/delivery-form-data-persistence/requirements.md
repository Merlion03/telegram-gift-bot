# Документ требований: Сохранение данных формы доставки

## Введение

Данная функциональность обеспечивает сохранение и восстановление ранее заполненных данных в форме доставки физического приза. Если пользователь уже отправлял данные для физического приза, но позже решил их изменить, форма должна автоматически заполниться сохранёнными данными из базы данных PostgreSQL.

## Глоссарий

- **Delivery_Form**: React-компонент формы доставки физического приза (DeliveryForm.tsx)
- **Prize_Repository**: Репозиторий для работы с данными призов в PostgreSQL
- **Backend_API**: Backend API endpoint для получения информации о призе
- **Delivery_Data**: Данные доставки (ФИО, адрес, телефон, комментарий)
- **Prize_ID**: Уникальный идентификатор приза в базе данных
- **Telegram_ID**: Уникальный идентификатор пользователя в Telegram
- **Claimed_At**: Временная метка первого заполнения формы доставки

## Требования

### Требование 1: Получение сохранённых данных доставки

**User Story:** Как пользователь, я хочу видеть ранее заполненные данные в форме доставки, чтобы не вводить их заново при изменении.

#### Критерии приёмки

1. WHEN Delivery_Form монтируется, THE Delivery_Form SHALL запросить информацию о призе через Backend_API
2. WHEN Backend_API возвращает Prize с заполненным claimed_at, THE Delivery_Form SHALL извлечь Delivery_Data из ответа
3. THE Backend_API SHALL включать все поля Delivery_Data в ответ (last_name, first_name, patronymic, country, postal_code, city, street, house, apartment, phone, comment)
4. IF Backend_API возвращает HTTP 404, THEN THE Delivery_Form SHALL отобразить пустую форму
5. IF Backend_API возвращает HTTP 503, THEN THE Delivery_Form SHALL отобразить сообщение об ошибке с возможностью повторной попытки

### Требование 2: Предзаполнение полей формы

**User Story:** Как пользователь, я хочу видеть мои сохранённые данные в полях формы, чтобы понять, какие данные были отправлены ранее.

#### Критерии приёмки

1. WHEN Delivery_Data получены из Backend_API, THE Delivery_Form SHALL установить значения всех полей формы из Delivery_Data
2. THE Delivery_Form SHALL предзаполнить обязательные поля (last_name, first_name, country, postal_code, city, street, house, phone)
3. THE Delivery_Form SHALL предзаполнить необязательные поля (patronymic, apartment, comment), если они присутствуют в Delivery_Data
4. IF поле в Delivery_Data равно NULL или пустой строке, THEN THE Delivery_Form SHALL оставить соответствующее поле формы пустым
5. THE Delivery_Form SHALL сохранить валидацию полей формы после предзаполнения

### Требование 3: Редактирование сохранённых данных

**User Story:** Как пользователь, я хочу изменить ранее заполненные данные, чтобы исправить ошибки или обновить информацию.

#### Критерии приёмки

1. WHEN форма предзаполнена сохранёнными данными, THE Delivery_Form SHALL разрешить редактирование всех полей
2. WHEN пользователь изменяет предзаполненные данные, THE Delivery_Form SHALL применить валидацию к изменённым значениям
3. WHEN пользователь отправляет изменённые данные, THE Delivery_Form SHALL отправить обновлённые данные через POST /api/delivery
4. THE Backend_API SHALL обновить существующие Delivery_Data в PostgreSQL через Prize_Repository.update_delivery_data_by_prize_id
5. THE Backend_API SHALL сохранить updated_at с текущей временной меткой UTC

### Требование 4: Индикация состояния загрузки

**User Story:** Как пользователь, я хочу видеть индикатор загрузки при получении данных, чтобы понимать, что система работает.

#### Критерии приёмки

1. WHILE Delivery_Form запрашивает данные из Backend_API, THE Delivery_Form SHALL отображать индикатор загрузки
2. THE Delivery_Form SHALL блокировать поля формы во время загрузки данных
3. WHEN данные успешно загружены, THE Delivery_Form SHALL скрыть индикатор загрузки и разблокировать поля
4. IF загрузка данных завершается ошибкой, THEN THE Delivery_Form SHALL скрыть индикатор загрузки и отобразить сообщение об ошибке

### Требование 5: Обработка отсутствующих данных

**User Story:** Как новый пользователь, я хочу видеть пустую форму при первом заполнении, чтобы ввести свои данные.

#### Критерии приёмки

1. WHEN Backend_API возвращает Prize с claimed_at равным NULL, THE Delivery_Form SHALL отобразить пустую форму
2. WHEN Backend_API возвращает Prize с пустыми полями Delivery_Data, THE Delivery_Form SHALL отобразить пустую форму
3. THE Delivery_Form SHALL применить стандартную валидацию к пустой форме
4. WHEN пользователь заполняет пустую форму и отправляет данные, THE Backend_API SHALL установить claimed_at в текущее время UTC

### Требование 6: Кэширование данных формы

**User Story:** Как пользователь, я хочу, чтобы данные формы загружались быстро, чтобы не ждать при каждом открытии.

#### Критерии приёмки

1. WHEN Delivery_Form успешно загружает данные из Backend_API, THE Delivery_Form SHALL кэшировать Delivery_Data в памяти компонента
2. IF пользователь закрывает и снова открывает форму в рамках одной сессии, THEN THE Delivery_Form SHALL использовать кэшированные данные
3. THE Delivery_Form SHALL очистить кэш при размонтировании компонента
4. THE Delivery_Form SHALL игнорировать кэш при явном запросе обновления данных

### Требование 7: Логирование операций с данными

**User Story:** Как разработчик, я хочу видеть логи операций с данными формы, чтобы отслеживать проблемы и производительность.

#### Критерии приёмки

1. WHEN Delivery_Form запрашивает данные из Backend_API, THE Delivery_Form SHALL логировать начало запроса с Prize_ID
2. WHEN Backend_API возвращает данные, THE Delivery_Form SHALL логировать успешное получение с временем выполнения
3. IF Backend_API возвращает ошибку, THEN THE Delivery_Form SHALL логировать код ошибки и сообщение
4. WHEN пользователь отправляет изменённые данные, THE Delivery_Form SHALL логировать количество изменённых полей

### Требование 8: Тестирование round-trip свойства

**User Story:** Как разработчик, я хочу убедиться, что данные сохраняются и восстанавливаются корректно, чтобы избежать потери данных.

#### Критерии приёмки

1. FOR ALL валидных Delivery_Data, сохранение через POST /api/delivery и последующее получение через Backend_API SHALL вернуть эквивалентные данные (round-trip property)
2. THE round-trip property SHALL сохранять все обязательные поля без изменений
3. THE round-trip property SHALL сохранять необязательные поля, если они были заполнены
4. THE round-trip property SHALL корректно обрабатывать пустые строки и NULL значения в необязательных полях
