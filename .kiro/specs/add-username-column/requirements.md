# Документ требований: Добавление столбца Username

## Введение

Данная функция добавляет новый столбец "Username" (ник пользователя в Telegram, например @Merlion) в Google Sheets таблицу после столбца "Telegram ID". Это улучшит удобство работы операторов с таблицей, позволяя быстро идентифицировать пользователей по их никам без необходимости искать их по числовому ID.

Текущая структура столбцов будет изменена: все столбцы после Telegram ID сдвинутся на одну позицию вправо, а новый столбец Username займёт позицию B.

## Глоссарий

- **GoogleSheetsService**: Сервис для работы с Google Sheets API, обеспечивающий поиск победителей и сохранение данных доставки
- **SyncService**: Сервис синхронизации данных между Google Sheets и PostgreSQL
- **Username**: Ник пользователя в Telegram в формате @username (может быть пустым, если у пользователя нет ника)
- **Telegram_ID**: Уникальный числовой идентификатор пользователя в Telegram
- **Code_Word**: Кодовое слово, определяющее worksheet в Google Sheets
- **Prize_Type**: Тип приза (digital или physical)
- **Delivery_Data**: Данные доставки для физических призов (ФИО, адрес, телефон, комментарий)

## Требования

### Требование 1: Обновление структуры столбцов Google Sheets

**User Story:** Как оператор, я хочу видеть ник пользователя в Telegram рядом с его Telegram ID, чтобы быстро идентифицировать пользователей при работе с таблицей.

#### Критерии приёмки

1. THE GoogleSheetsService SHALL читать данные из столбца B (Username) при поиске победителя
2. THE GoogleSheetsService SHALL читать данные типа приза из столбца C (сдвинуто с B)
3. THE GoogleSheetsService SHALL читать промокод из столбца D (сдвинуто с C) для цифровых призов
4. THE GoogleSheetsService SHALL читать инструкции из столбца E (сдвинуто с D) для цифровых призов
5. THE GoogleSheetsService SHALL читать данные доставки из столбцов F-N (сдвинуто с E-M) для физических призов

### Требование 2: Синхронизация данных с учётом нового столбца

**User Story:** Как система, я хочу корректно синхронизировать данные из Google Sheets в PostgreSQL с учётом нового столбца Username, чтобы обеспечить консистентность данных.

#### Критерии приёмки

1. THE SyncService SHALL читать Username из столбца B (индекс 1) при синхронизации данных
2. THE SyncService SHALL читать Code_Word из столбца C (индекс 2, сдвинуто с B)
3. THE SyncService SHALL читать Prize_Type из столбца D (индекс 3, сдвинуто с C)
4. THE SyncService SHALL читать промокод из столбца E (индекс 4, сдвинуто с D) для цифровых призов
5. THE SyncService SHALL читать инструкции из столбца F (индекс 5, сдвинуто с E) для цифровых призов
6. THE SyncService SHALL читать данные доставки из столбцов G-O (индексы 6-14, сдвинуто с F-N) для физических призов
7. WHEN Username присутствует в строке, THE SyncService SHALL сохранять его в базу данных
8. WHEN Username отсутствует в строке, THE SyncService SHALL сохранять NULL в базу данных

### Требование 3: Сохранение данных доставки с учётом нового столбца

**User Story:** Как система, я хочу корректно сохранять данные доставки в правильные столбцы Google Sheets с учётом сдвига, чтобы данные записывались в нужные ячейки.

#### Критерии приёмки

1. THE GoogleSheetsService SHALL сохранять фамилию в столбец F (сдвинуто с E) для физических призов
2. THE GoogleSheetsService SHALL сохранять имя в столбец G (сдвинуто с F) для физических призов
3. THE GoogleSheetsService SHALL сохранять отчество в столбец H (сдвинуто с G) для физических призов
4. THE GoogleSheetsService SHALL сохранять город в столбец I (сдвинуто с H) для физических призов
5. THE GoogleSheetsService SHALL сохранять улицу в столбец J (сдвинуто с I) для физических призов
6. THE GoogleSheetsService SHALL сохранять дом в столбец K (сдвинуто с J) для физических призов
7. THE GoogleSheetsService SHALL сохранять квартиру в столбец L (сдвинуто с K) для физических призов
8. THE GoogleSheetsService SHALL сохранять телефон в столбец M (сдвинуто с L) для физических призов
9. THE GoogleSheetsService SHALL сохранять комментарий в столбец N (сдвинуто с M) для физических призов
10. THE GoogleSheetsService SHALL сохранять время получения приза в столбец O (сдвинуто с N) для физических призов

### Требование 4: Расширение схемы базы данных

**User Story:** Как разработчик, я хочу хранить Username в базе данных PostgreSQL, чтобы иметь возможность использовать эту информацию в приложении без обращения к Google Sheets.

#### Критерии приёмки

1. THE Database_Schema SHALL включать столбец username типа VARCHAR в таблице prizes
2. THE Database_Schema SHALL разрешать NULL значения для столбца username
3. THE Database_Schema SHALL применять миграцию для добавления столбца username к существующей таблице prizes

### Требование 5: Обратная совместимость

**User Story:** Как система, я хочу корректно обрабатывать существующие данные без столбца Username, чтобы не нарушить работу с историческими данными.

#### Критерии приёмки

1. WHEN строка в Google Sheets не содержит Username, THE SyncService SHALL успешно синхронизировать остальные данные
2. WHEN строка в Google Sheets содержит пустой Username, THE SyncService SHALL сохранять NULL в базу данных
3. THE GoogleSheetsService SHALL корректно читать данные из строк без Username
4. THE SyncService SHALL валидировать минимальную структуру строки (Telegram_ID, Username, Code_Word, Prize_Type) перед синхронизацией

### Требование 6: Покрытие тестами

**User Story:** Как разработчик, я хочу иметь полное покрытие тестами для новой функциональности, чтобы гарантировать корректность работы и предотвратить регрессии.

#### Критерии приёмки

1. THE Test_Suite SHALL включать unit-тесты для чтения Username из GoogleSheetsService
2. THE Test_Suite SHALL включать unit-тесты для синхронизации Username через SyncService
3. THE Test_Suite SHALL включать unit-тесты для сохранения данных доставки в правильные столбцы
4. THE Test_Suite SHALL включать integration-тесты для проверки корректности индексов столбцов
5. THE Test_Suite SHALL включать тесты для обработки пустых и NULL значений Username
6. FOR ALL тестов с Google Sheets данными, парсинг затем форматирование затем парсинг SHALL возвращать эквивалентный объект (round-trip property)
