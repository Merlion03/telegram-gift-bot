# Документ требований: Поддержка медиа-сообщений в Telegram-боте

## Введение

Данная функциональность расширяет существующий Telegram-бот и веб-админку для обработки, хранения и отображения медиа-контента (фото, видео, анимации, стикеры, голосовые сообщения, документы). В настоящее время система обрабатывает только текстовые сообщения. Новая функциональность обеспечит полноценную работу с мультимедийным контентом, включая автоматическое скачивание файлов на сервер (из-за ограничения времени жизни ссылок Telegram ~1 час) и корректное отображение в веб-интерфейсе.

## Глоссарий

- **Telegram_Bot**: Python-приложение, обрабатывающее входящие сообщения от пользователей Telegram
- **WebApp**: Next.js веб-приложение (админка) для отображения и управления данными
- **Database**: PostgreSQL база данных для хранения сообщений и метаданных медиафайлов
- **Media_Handler**: модуль Telegram-бота, отвечающий за обработку медиа-контента
- **File_Storage**: локальная файловая система сервера для хранения скачанных медиафайлов
- **Message_Table**: таблица в PostgreSQL для хранения сообщений чата
- **Media_Type**: тип медиа-контента (text, photo, video, animation, sticker, voice, document)
- **File_ID**: уникальный идентификатор файла в Telegram API
- **File_Path**: путь к сохраненному файлу на сервере относительно корня проекта
- **Caption**: текстовое описание, прикрепленное к медиафайлу
- **Media_Renderer**: компонент WebApp для динамического отображения медиа-контента

## Требования

### Требование 1: Расширение схемы базы данных для медиа-контента

**User Story:** Как разработчик системы, я хочу хранить метаданные медиафайлов в базе данных, чтобы обеспечить быстрый доступ к информации о типе контента и его расположении.

#### Критерии приемки

1. THE Database SHALL содержать поле `media_type` в Message_Table для хранения типа контента
2. THE Database SHALL содержать поле `file_path` в Message_Table для хранения пути к файлу на сервере
3. THE Database SHALL содержать поле `file_id` в Message_Table для хранения Telegram File_ID
4. THE Database SHALL содержать поле `caption` в Message_Table для хранения текстового описания медиафайла
5. WHEN поле `media_type` имеет значение "text", THE Database SHALL допускать NULL значения для полей `file_path` и `file_id`
6. THE Database SHALL поддерживать следующие значения Media_Type: text, photo, video, animation, sticker, voice, document

### Требование 2: Обработка входящих медиа-сообщений в Telegram-боте

**User Story:** Как пользователь Telegram, я хочу отправлять боту медиафайлы любого типа, чтобы они сохранялись и отображались в админке.

#### Критерии приемки

1. WHEN пользователь отправляет фото, THE Telegram_Bot SHALL извлечь File_ID из сообщения
2. WHEN пользователь отправляет видео, THE Telegram_Bot SHALL извлечь File_ID из сообщения
3. WHEN пользователь отправляет анимацию (GIF), THE Telegram_Bot SHALL извлечь File_ID из сообщения
4. WHEN пользователь отправляет стикер, THE Telegram_Bot SHALL извлечь File_ID из сообщения
5. WHEN пользователь отправляет голосовое сообщение, THE Telegram_Bot SHALL извлечь File_ID из сообщения
6. WHEN пользователь отправляет документ, THE Telegram_Bot SHALL извлечь File_ID из сообщения
7. WHEN медиафайл содержит Caption, THE Telegram_Bot SHALL сохранить Caption в Database вместе с метаданными файла
8. THE Media_Handler SHALL определить Media_Type для каждого входящего сообщения

### Требование 3: Автоматическое скачивание медиафайлов на сервер

**User Story:** Как администратор системы, я хочу, чтобы медиафайлы автоматически скачивались на сервер, чтобы обеспечить их доступность после истечения времени жизни ссылок Telegram.

#### Критерии приемки

1. WHEN Telegram_Bot получает медиафайл, THE Media_Handler SHALL скачать файл на File_Storage в течение 30 секунд
2. THE Media_Handler SHALL сохранить файл в директорию `telegram-bot/media/{media_type}/{chat_id}/`
3. THE Media_Handler SHALL генерировать уникальное имя файла используя формат `{timestamp}_{file_id}.{extension}`
4. WHEN файл успешно скачан, THE Media_Handler SHALL сохранить File_Path в Database
5. IF скачивание файла завершилось ошибкой, THEN THE Media_Handler SHALL записать ошибку в лог и сохранить сообщение с media_type, но без file_path
6. THE Media_Handler SHALL сохранять оригинальное расширение файла при скачивании
7. WHEN стикер имеет формат TGS (анимированный), THE Media_Handler SHALL сохранить файл с расширением `.tgs`
8. WHEN стикер имеет формат WEBM (видео-стикер), THE Media_Handler SHALL сохранить файл с расширением `.webm`

### Требование 4: Конвертация стикеров для веб-отображения

**User Story:** Как пользователь админки, я хочу видеть стикеры в веб-интерфейсе, чтобы полноценно просматривать историю сообщений.

#### Критерии приемки

1. WHEN Media_Handler скачивает стикер формата TGS, THE Media_Handler SHALL конвертировать его в формат GIF или WebP для веб-отображения
2. WHEN Media_Handler скачивает стикер формата WEBM, THE Media_Handler SHALL сохранить оригинальный файл без конвертации
3. WHEN Media_Handler скачивает статичный стикер формата WEBP, THE Media_Handler SHALL сохранить оригинальный файл без конвертации
4. IF конвертация стикера завершилась ошибкой, THEN THE Media_Handler SHALL сохранить оригинальный файл и записать предупреждение в лог
5. THE Media_Handler SHALL сохранить путь к конвертированному файлу в Database как file_path

### Требование 5: API для доступа к медиафайлам из WebApp

**User Story:** Как разработчик WebApp, я хочу получать медиафайлы через API, чтобы отображать их в веб-интерфейсе.

#### Критерии приемки

1. THE WebApp SHALL предоставить API endpoint `/api/media/{file_path}` для получения медиафайлов
2. WHEN WebApp получает запрос к медиафайлу, THE WebApp SHALL проверить существование файла на File_Storage
3. WHEN файл существует, THE WebApp SHALL вернуть файл с корректным Content-Type заголовком
4. IF файл не существует, THEN THE WebApp SHALL вернуть HTTP статус 404
5. THE WebApp SHALL устанавливать заголовок Cache-Control для оптимизации загрузки медиафайлов
6. THE WebApp SHALL поддерживать следующие Content-Type: image/jpeg, image/png, image/gif, image/webp, video/mp4, video/webm, audio/ogg, application/octet-stream

### Требование 6: Динамическое отображение медиа-контента в WebApp

**User Story:** Как администратор, я хочу видеть медиафайлы в истории сообщений, чтобы полноценно анализировать коммуникацию с пользователями.

#### Критерии приемки

1. WHEN сообщение имеет media_type "photo", THE Media_Renderer SHALL отобразить изображение через HTML элемент `<img>`
2. WHEN сообщение имеет media_type "video", THE Media_Renderer SHALL отобразить видео через HTML элемент `<video>` с контролами воспроизведения
3. WHEN сообщение имеет media_type "animation", THE Media_Renderer SHALL отобразить анимацию через HTML элемент `<video>` с автовоспроизведением и зацикливанием
4. WHEN сообщение имеет media_type "sticker", THE Media_Renderer SHALL отобразить стикер через HTML элемент `<img>` или `<video>` в зависимости от формата
5. WHEN сообщение имеет media_type "voice", THE Media_Renderer SHALL отобразить аудиоплеер через HTML элемент `<audio>` с контролами воспроизведения
6. WHEN сообщение имеет media_type "document", THE Media_Renderer SHALL отобразить кнопку-ссылку для скачивания файла
7. WHEN медиафайл имеет Caption, THE Media_Renderer SHALL отобразить Caption под медиа-элементом
8. WHEN сообщение имеет media_type "text", THE Media_Renderer SHALL отобразить текст как обычное текстовое сообщение

### Требование 7: Обработка ошибок загрузки медиафайлов

**User Story:** Как пользователь админки, я хочу видеть информативные сообщения об ошибках, чтобы понимать, почему медиафайл недоступен.

#### Критерии приемки

1. WHEN медиафайл не может быть загружен в WebApp, THE Media_Renderer SHALL отобразить placeholder с иконкой типа файла
2. WHEN медиафайл отсутствует на File_Storage, THE Media_Renderer SHALL отобразить сообщение "Файл недоступен"
3. IF загрузка изображения завершилась ошибкой, THEN THE Media_Renderer SHALL отобразить альтернативный текст с типом медиа
4. THE Media_Renderer SHALL логировать ошибки загрузки медиафайлов в консоль браузера для отладки

### Требование 8: Миграция базы данных для поддержки медиа-контента

**User Story:** Как администратор системы, я хочу безопасно обновить схему базы данных, чтобы добавить поддержку медиа-контента без потери существующих данных.

#### Критерии приемки

1. THE Database SHALL выполнить миграцию для добавления полей `media_type`, `file_path`, `file_id`, `caption` в Message_Table
2. WHEN миграция выполняется, THE Database SHALL установить значение "text" для поля `media_type` всех существующих записей
3. WHEN миграция выполняется, THE Database SHALL установить NULL для полей `file_path`, `file_id`, `caption` всех существующих записей
4. THE Database SHALL создать индекс на поле `media_type` для оптимизации запросов фильтрации по типу контента
5. IF миграция завершилась ошибкой, THEN THE Database SHALL выполнить откат изменений и сохранить исходное состояние схемы

### Требование 9: Управление хранилищем медиафайлов

**User Story:** Как администратор системы, я хочу контролировать использование дискового пространства, чтобы предотвратить переполнение хранилища.

#### Критерии приемки

1. THE File_Storage SHALL организовать файлы в структуру директорий по типу медиа и chat_id
2. THE Media_Handler SHALL создавать необходимые директории автоматически при первом сохранении файла
3. THE File_Storage SHALL устанавливать права доступа к директориям медиафайлов только для чтения веб-сервером
4. WHEN размер файла превышает 20 МБ, THE Media_Handler SHALL записать предупреждение в лог
5. THE Media_Handler SHALL сохранять размер файла в байтах в Database для мониторинга использования хранилища

### Требование 10: Модульная архитектура обработки медиа

**User Story:** Как разработчик системы, я хочу иметь модульную архитектуру обработки медиа, чтобы легко добавлять поддержку новых типов контента в будущем.

#### Критерии приемки

1. THE Media_Handler SHALL быть реализован как отдельный модуль в файле `telegram-bot/handlers/media_handler.py`
2. THE Media_Handler SHALL использовать отдельный модуль `telegram-bot/services/file_downloader.py` для скачивания файлов
3. THE Media_Handler SHALL использовать отдельный модуль `telegram-bot/services/sticker_converter.py` для конвертации стикеров
4. THE WebApp SHALL реализовать Media_Renderer как отдельный React компонент в файле `nextjs-app/components/MediaRenderer.tsx`
5. THE WebApp SHALL реализовать API endpoint в отдельном файле `nextjs-app/app/api/media/[...path]/route.ts`
6. THE Database SHALL использовать отдельный файл миграции `telegram-bot/migrations/add_media_support.sql`

## Архитектурные ограничения

1. Все модули должны следовать принципу единственной ответственности (один модуль = один файл)
2. Код должен быть написан на русском языке (комментарии, переменные где применимо)
3. Обязательное использование виртуального окружения Python для всех скриптов
4. Максимальная масштабируемость и готовность к добавлению новых типов медиа
5. Обработка всех ошибок с подробным логированием
6. Никаких костылей — только правильные архитектурные решения

## Технические зависимости

- Python 3.x с виртуальным окружением
- Telegram Bot API (python-telegram-bot или aiogram)
- PostgreSQL для хранения метаданных
- Next.js/React для веб-интерфейса
- Библиотека для конвертации TGS стикеров (например, lottie или rlottie)
- Файловая система сервера для хранения медиафайлов
