# Документ требований: Сохранение всех диалогов с ботом в админке

## Введение

Текущая система сохраняет в админке только те диалоги, где пользователь явно нажал кнопку "Позвать человека". Это ограничивает возможности администратора по мониторингу взаимодействия пользователей с ботом и проактивной поддержке.

Данная фича добавляет автоматическое сохранение всех диалогов с ботом в базу данных и отображение их в админ-панели, позволяя администратору в любой момент просмотреть историю общения и подключиться к диалогу.

## Глоссарий

- **Bot_Message_Handler** - обработчик сообщений бота, который перехватывает все входящие сообщения от пользователей
- **Chat_Session** - сессия диалога пользователя с ботом, автоматически создаваемая при первом сообщении
- **Admin_Panel** - веб-интерфейс администратора по адресу /admin
- **Support_Session** - специальная сессия поддержки, создаваемая при нажатии кнопки "Позвать человека"
- **Message_Repository** - репозиторий для работы с сообщениями в базе данных
- **Session_Manager** - сервис управления сессиями диалогов
- **User** - пользователь Telegram бота
- **Administrator** - администратор системы, работающий через Admin_Panel

## Требования

### Требование 1: Автоматическое создание сессий диалога

**User Story:** Как администратор, я хочу видеть все диалоги пользователей с ботом, чтобы иметь полную картину взаимодействия и возможность проактивной поддержки.

#### Критерии приёмки

1. WHEN User отправляет первое сообщение боту, THE Bot_Message_Handler SHALL создать новую Chat_Session для этого User
2. WHEN User отправляет сообщение и у него уже существует активная Chat_Session, THE Bot_Message_Handler SHALL использовать существующую Chat_Session
3. THE Chat_Session SHALL содержать telegram_id пользователя, временную метку создания и статус активности
4. THE Chat_Session SHALL автоматически создаваться до обработки любой бизнес-логики бота
5. WHERE User нажимает кнопку "Позвать человека", THE System SHALL преобразовать Chat_Session в Support_Session с сохранением всей истории сообщений

### Требование 2: Сохранение всех сообщений пользователя

**User Story:** Как администратор, я хочу видеть полную историю сообщений каждого пользователя, чтобы понимать контекст его обращений.

#### Критерии приёмки

1. WHEN User отправляет текстовое сообщение, THE Message_Repository SHALL сохранить его в базу данных с привязкой к Chat_Session
2. WHEN User отправляет медиа-контент (фото, документ, видео, аудио, голосовое), THE Message_Repository SHALL сохранить file_id и текст caption
3. THE Message_Repository SHALL сохранять временную метку каждого сообщения
4. THE Message_Repository SHALL сохранять тип сообщения (from_user или from_bot)
5. WHEN Bot отправляет ответное сообщение User, THE Message_Repository SHALL сохранить его с типом from_bot

### Требование 3: Отображение всех диалогов в админ-панели

**User Story:** Как администратор, я хочу видеть список всех активных и недавних диалогов в админ-панели, чтобы выбрать нужный для просмотра или подключения.

#### Критерии приёмки

1. THE Admin_Panel SHALL отображать список всех Chat_Session, отсортированных по времени последнего сообщения
2. THE Admin_Panel SHALL показывать для каждой Chat_Session: telegram_id пользователя, время последнего сообщения, статус (активная/закрытая), тип (обычный диалог/поддержка)
3. THE Admin_Panel SHALL визуально различать обычные Chat_Session и Support_Session
4. WHEN Administrator выбирает Chat_Session из списка, THE Admin_Panel SHALL отобразить полную историю сообщений этой сессии
5. THE Admin_Panel SHALL автоматически обновлять список сессий при появлении новых сообщений

### Требование 4: Подключение администратора к любому диалогу

**User Story:** Как администратор, я хочу иметь возможность написать пользователю в любой момент, даже если он не нажимал "Позвать человека", чтобы предложить помощь проактивно.

#### Критерии приёмки

1. WHEN Administrator выбирает любую Chat_Session, THE Admin_Panel SHALL предоставить интерфейс для отправки сообщений
2. WHEN Administrator отправляет сообщение через Admin_Panel, THE System SHALL доставить его User в Telegram
3. WHEN Administrator отправляет первое сообщение в обычную Chat_Session, THE System SHALL автоматически преобразовать её в Support_Session
4. THE System SHALL сохранять все сообщения Administrator в Message_Repository с типом from_support
5. WHEN Administrator отправляет сообщение, THE User SHALL получить уведомление в Telegram с текстом сообщения

### Требование 5: Управление жизненным циклом сессий

**User Story:** Как система, я должна корректно управлять жизненным циклом сессий, чтобы не засорять базу данных и обеспечить корректную работу.

#### Критерии приёмки

1. WHEN Chat_Session не имеет активности более 24 часов, THE Session_Manager SHALL автоматически закрыть её
2. WHEN Administrator закрывает Support_Session, THE System SHALL обновить статус сессии на "closed" и установить временную метку закрытия
3. THE Admin_Panel SHALL отображать закрытые сессии отдельно от активных
4. WHERE Administrator фильтрует список сессий, THE Admin_Panel SHALL предоставить фильтры по статусу (активные/закрытые) и типу (обычные/поддержка)
5. THE System SHALL сохранять закрытые сессии в базе данных для истории

### Требование 6: Обратная совместимость с существующей функциональностью

**User Story:** Как разработчик, я хочу сохранить работоспособность существующей функции "Позвать человека", чтобы не сломать текущий функционал.

#### Критерии приёмки

1. WHEN User нажимает кнопку "Позвать человека", THE System SHALL работать так же, как и раньше
2. THE System SHALL сохранять существующую логику FSM состояний для Support_Session
3. WHEN User находится в Support_Session, THE System SHALL продолжать использовать клавиатуру "Завершить диалог"
4. THE System SHALL корректно обрабатывать переход из обычной Chat_Session в Support_Session
5. FOR ALL существующих тестов поддержки, выполнение SHALL завершаться успешно без изменений

### Требование 7: Производительность и масштабируемость

**User Story:** Как система, я должна эффективно обрабатывать большое количество диалогов, чтобы обеспечить быструю работу админ-панели.

#### Критерии приёмки

1. WHEN Admin_Panel загружает список сессий, THE System SHALL использовать пагинацию для отображения не более 50 сессий на странице
2. THE System SHALL использовать индексы базы данных для быстрого поиска сессий по telegram_id и временным меткам
3. WHEN количество сообщений в Chat_Session превышает 100, THE Admin_Panel SHALL использовать ленивую загрузку истории сообщений
4. THE System SHALL выполнять запросы к базе данных с оптимизацией (eager loading для связанных сущностей)
5. WHEN Admin_Panel обновляет список сессий, THE System SHALL загружать только изменившиеся данные, а не весь список

### Требование 8: Безопасность и права доступа

**User Story:** Как администратор системы, я хочу быть уверенным, что только авторизованные администраторы имеют доступ к диалогам пользователей.

#### Критерии приёмки

1. THE Admin_Panel SHALL требовать аутентификацию перед отображением списка сессий
2. WHEN неавторизованный пользователь пытается получить доступ к /admin, THE System SHALL перенаправить его на страницу входа
3. THE System SHALL логировать все действия Administrator в диалогах (просмотр, отправка сообщений, закрытие сессий)
4. THE System SHALL не отображать в Admin_Panel системные сообщения бота (команды /start, /help)
5. THE System SHALL защищать API endpoints для работы с сессиями от несанкционированного доступа

## Технические ограничения

- Использовать существующую схему базы данных с минимальными изменениями
- Сохранить модульную архитектуру проекта (один модуль = один файл)
- Все новые компоненты должны иметь unit-тесты
- Использовать существующие паттерны логирования (structlog)
- Следовать принципу единственной ответственности для всех новых модулей

## Зависимости

- Существующая модель SupportSession и SupportMessage
- Существующий SupportRepository
- Существующая админ-панель Next.js
- Существующие обработчики бота (CommonHandler, PrizeHandler, SupportHandler)
- Существующая система FSM состояний
