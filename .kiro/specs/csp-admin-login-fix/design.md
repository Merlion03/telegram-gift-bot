# CSP Admin Login Fix - Дизайн исправления

## Обзор

Исправление бага с Content-Security-Policy (CSP) для страниц админки (`/admin`) и логина (`/login`). Несмотря на то, что middleware настроен на применение мягкой CSP с `'unsafe-inline'` для этих роутов, браузер получает строгую CSP политику `script-src 'self'` без `'unsafe-inline'`, что блокирует критически важные inline-скрипты Next.js, необходимые для гидратации Client Components.

Стратегия исправления: выявить причину переопределения CSP заголовков и обеспечить корректное применение мягкой политики для роутов `/login` и `/admin`, сохраняя при этом строгую CSP для остальных страниц.

## Глоссарий

- **Bug_Condition (C)**: Условие, при котором проявляется баг - когда пользователь открывает страницы `/login` или `/admin`, и браузер применяет строгую CSP вместо мягкой
- **Property (P)**: Желаемое поведение - браузер должен применять CSP с директивой `script-src 'self' 'unsafe-inline'` для страниц `/login` и `/admin`
- **Preservation**: Существующее поведение, которое должно остаться неизменным - мягкая CSP для `/webapp`, строгая CSP для остальных роутов, корректная работа аутентификации
- **middleware.ts**: Файл Next.js middleware, который устанавливает заголовки безопасности для всех запросов
- **buildWebAppCSPHeader()**: Функция в middleware, которая формирует мягкую CSP политику с `'unsafe-inline'`
- **Client Component**: React-компонент с директивой `'use client'`, который требует гидратации на клиенте и использует inline-скрипты Next.js
- **CSP (Content-Security-Policy)**: HTTP-заголовок безопасности, контролирующий источники загрузки ресурсов для защиты от XSS-атак
- **Гидратация (Hydration)**: Процесс, при котором Next.js "оживляет" серверный HTML, добавляя интерактивность через React на клиенте

## Детали бага

### Условие проявления бага (Fault Condition)

Баг проявляется, когда пользователь открывает страницы `/login` или `/admin` в браузере. Middleware корректно определяет эти роуты как требующие мягкой CSP и вызывает функцию `buildWebAppCSPHeader()`, которая формирует политику с `'unsafe-inline'`. Однако браузер получает строгую CSP политику `script-src 'self'` без `'unsafe-inline'`, что приводит к блокировке inline-скриптов Next.js.

**Формальная спецификация:**
```
FUNCTION isBugCondition(request)
  INPUT: request типа NextRequest
  OUTPUT: boolean
  
  pathname := request.nextUrl.pathname
  
  RETURN (pathname.startsWith('/login') OR pathname.startsWith('/admin'))
         AND browserReceivedCSP.scriptSrc NOT CONTAINS 'unsafe-inline'
         AND middlewareSetCSP.scriptSrc CONTAINS 'unsafe-inline'
END FUNCTION
```

### Примеры

- **Пример 1**: Пользователь открывает `/login` → Middleware устанавливает CSP с `'unsafe-inline'` → Браузер получает CSP без `'unsafe-inline'` → Inline-скрипты Next.js блокируются → Страница не работает
- **Пример 2**: Пользователь открывает `/admin` → Middleware устанавливает CSP с `'unsafe-inline'` → Браузер получает CSP без `'unsafe-inline'` → React-компоненты не гидратируются → Интерактивность не работает
- **Пример 3**: Пользователь открывает `/webapp` → Middleware устанавливает CSP с `'unsafe-inline'` → Браузер корректно получает CSP с `'unsafe-inline'` → Страница работает нормально (существующее поведение)
- **Граничный случай**: Пользователь открывает `/admin/some-subpage` → Должна применяться та же мягкая CSP, что и для `/admin`

## Ожидаемое поведение

### Требования к сохранению (Preservation Requirements)

**Неизменное поведение:**
- Мягкая CSP для `/webapp` должна продолжать работать точно так же, как сейчас
- Строгая CSP для всех остальных роутов (не `/webapp`, `/login`, `/admin`) должна оставаться неизменной
- Проверка аутентификации для защищённых роутов должна работать корректно
- Редирект неавторизованных пользователей на страницу логина должен работать
- Дополнительные заголовки безопасности (X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy) должны устанавливаться корректно

**Область действия:**
Все запросы, которые НЕ относятся к роутам `/login` или `/admin`, должны быть полностью не затронуты этим исправлением. Это включает:
- Запросы к `/webapp` и его подстраницам
- Запросы к API endpoints (`/api/*`)
- Запросы к статическим ресурсам
- Запросы к любым другим страницам приложения

## Гипотеза о первопричине

На основе анализа кода и описания бага, наиболее вероятные причины:

1. **Конфликт порядка установки заголовков**: Next.js может устанавливать собственные CSP заголовки после выполнения middleware, переопределяя заголовки, установленные в middleware. В Next.js 13+ с App Router порядок применения заголовков может отличаться от Pages Router.

2. **Проблема с NextResponse.next()**: Метод `NextResponse.next()` может не корректно передавать заголовки в цепочку обработки запроса. Возможно, заголовки теряются или переопределяются на следующих этапах рендеринга.

3. **Специфика Client Components**: Страницы `/login` и `/admin` используют директиву `'use client'`, что делает их Client Components. Next.js может применять специальную обработку CSP для Client Components, игнорируя заголовки из middleware.

4. **Кэширование заголовков**: Браузер или промежуточные прокси могут кэшировать старые CSP заголовки, и изменения в middleware не применяются немедленно.

5. **Проблема с matcher конфигурацией**: Matcher в `middleware.ts` может некорректно обрабатывать роуты `/login` и `/admin`, хотя код показывает, что matcher должен применяться ко всем путям кроме статических ресурсов.

## Correctness Properties

Property 1: Fault Condition - CSP с unsafe-inline для /login и /admin

_Для любого_ HTTP-запроса, где путь начинается с `/login` или `/admin`, исправленный middleware SHALL устанавливать заголовок `Content-Security-Policy` с директивой `script-src 'self' 'unsafe-inline'`, и браузер SHALL получать и применять именно эту политику, позволяя выполнение inline-скриптов Next.js.

**Validates: Requirements 2.1, 2.2, 2.3, 2.4**

Property 2: Preservation - Неизменное поведение для других роутов

_Для любого_ HTTP-запроса, где путь НЕ начинается с `/login` или `/admin`, исправленный код SHALL применять ту же CSP политику, что и оригинальный код: мягкую CSP для `/webapp` и строгую CSP для всех остальных роутов, сохраняя существующее поведение безопасности и аутентификации.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4**

## Реализация исправления

### Необходимые изменения

Предполагая, что наш анализ первопричины верен:

**Файл**: `nextjs-app/middleware.ts`

**Функция**: `middleware()`

**Конкретные изменения**:

1. **Исследование проблемы**: Добавить логирование для отладки и понимания, какие заголовки фактически устанавливаются и передаются браузеру. Это поможет подтвердить или опровергнуть гипотезу.

2. **Изменение способа установки заголовков**: Вместо использования `NextResponse.next()` с последующей установкой заголовков, попробовать создать новый Response с явно установленными заголовками:
   ```typescript
   const response = NextResponse.next({
     request: {
       headers: new Headers(request.headers),
     },
   });
   ```

3. **Альтернативный подход - использование next.config.js**: Если проблема в порядке применения заголовков, можно добавить CSP настройки в `next.config.js` с условной логикой для разных роутов.

4. **Использование nonce для CSP**: Вместо `'unsafe-inline'` использовать nonce-based CSP, который является более безопасным подходом и лучше поддерживается Next.js:
   - Генерировать уникальный nonce для каждого запроса
   - Передавать nonce в CSP заголовок
   - Next.js автоматически добавит nonce к своим inline-скриптам

5. **Проверка и корректировка matcher**: Убедиться, что matcher корректно применяется к роутам `/login` и `/admin`, и не исключает их из обработки middleware.

### Рекомендуемый подход (на основе best practices Next.js)

Использовать **nonce-based CSP** вместо `'unsafe-inline'`:

```typescript
// Генерация nonce
import { randomBytes } from 'crypto';

export async function middleware(request: NextRequest) {
  const nonce = randomBytes(16).toString('base64');
  
  // Установка CSP с nonce
  const cspHeader = needsRelaxedCsp
    ? `script-src 'self' 'nonce-${nonce}'; ...`
    : buildCSPHeader();
  
  // Передача nonce в headers для использования в layout
  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-nonce', nonce);
  
  const response = NextResponse.next({
    request: {
      headers: requestHeaders,
    },
  });
  
  response.headers.set('Content-Security-Policy', cspHeader);
  
  return response;
}
```

Затем в `app/layout.tsx` использовать nonce для скриптов:
```typescript
import { headers } from 'next/headers';

export default function RootLayout({ children }) {
  const nonce = headers().get('x-nonce');
  // Next.js автоматически добавит nonce к inline-скриптам
}
```

## Стратегия тестирования

### Подход к валидации

Стратегия тестирования следует двухфазному подходу: сначала продемонстрировать баг на неисправленном коде через exploratory тесты, затем проверить, что исправление работает корректно и сохраняет существующее поведение.

### Exploratory Fault Condition Checking

**Цель**: Продемонстрировать баг ДО реализации исправления. Подтвердить или опровергнуть анализ первопричины. Если опровергнем, потребуется пересмотреть гипотезу.

**План тестирования**: Написать тесты, которые симулируют HTTP-запросы к `/login` и `/admin`, проверяют заголовки CSP в response от middleware, и затем проверяют, какие заголовки фактически получает браузер. Запустить эти тесты на НЕИСПРАВЛЕННОМ коде для наблюдения ошибок и понимания первопричины.

**Тестовые случаи**:
1. **Тест /login CSP**: Запрос к `/login` → Проверить CSP в middleware response → Проверить CSP в браузере (будет fail на неисправленном коде)
2. **Тест /admin CSP**: Запрос к `/admin` → Проверить CSP в middleware response → Проверить CSP в браузере (будет fail на неисправленном коде)
3. **Тест /admin/subpage CSP**: Запрос к `/admin/dashboard` → Проверить CSP применяется корректно (может fail на неисправленном коде)
4. **Тест inline-скриптов**: Загрузить страницу `/login` в браузере → Проверить, что Next.js inline-скрипты выполняются (будет fail на неисправленном коде)

**Ожидаемые контрпримеры**:
- Middleware устанавливает CSP с `'unsafe-inline'`, но браузер получает CSP без `'unsafe-inline'`
- Возможные причины: переопределение заголовков Next.js, проблема с NextResponse.next(), специфика Client Components

### Fix Checking

**Цель**: Проверить, что для всех запросов, где выполняется условие бага, исправленная функция производит ожидаемое поведение.

**Псевдокод:**
```
FOR ALL request WHERE isBugCondition(request) DO
  response := middleware_fixed(request)
  browserCSP := getBrowserReceivedCSP(response)
  ASSERT browserCSP.scriptSrc CONTAINS 'unsafe-inline' OR browserCSP.scriptSrc CONTAINS nonce
  ASSERT nextJsInlineScripts ARE NOT BLOCKED
END FOR
```

### Preservation Checking

**Цель**: Проверить, что для всех запросов, где условие бага НЕ выполняется, исправленная функция производит тот же результат, что и оригинальная функция.

**Псевдокод:**
```
FOR ALL request WHERE NOT isBugCondition(request) DO
  ASSERT middleware_original(request).headers = middleware_fixed(request).headers
  ASSERT middleware_original(request).redirect = middleware_fixed(request).redirect
END FOR
```

**Подход к тестированию**: Property-based тестирование рекомендуется для preservation checking, потому что:
- Автоматически генерирует множество тестовых случаев по всему домену входных данных
- Выявляет граничные случаи, которые могут быть пропущены в ручных unit-тестах
- Предоставляет сильные гарантии, что поведение не изменилось для всех не-багованных входных данных

**План тестирования**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для роутов `/webapp` и других страниц, затем написать property-based тесты, фиксирующие это поведение.

**Тестовые случаи**:
1. **Preservation /webapp CSP**: Наблюдать, что `/webapp` получает мягкую CSP на неисправленном коде → Написать тест для проверки, что это продолжает работать после исправления
2. **Preservation строгой CSP**: Наблюдать, что другие роуты получают строгую CSP на неисправленном коде → Написать тест для проверки сохранения этого поведения
3. **Preservation аутентификации**: Наблюдать, что редирект на `/login` работает для неавторизованных пользователей → Проверить сохранение после исправления
4. **Preservation других заголовков**: Проверить, что X-Frame-Options, X-Content-Type-Options и другие заголовки устанавливаются корректно
