# Дизайн исправления багов отображения сообщений в чате

## Обзор

Данный документ описывает техническое решение для исправления двух критических багов в компоненте ChatWindow:

1. **Неправильное отображение отправителя**: Сообщения от администратора отображаются как сообщения от пользователя из-за неправильного преобразования типа отправителя при получении через WebSocket
2. **Дублирование разделителей дат**: После перезагрузки страницы функция группировки создаёт несколько разделителей для одной даты из-за некорректной логики сравнения дат

Оба бага связаны с логикой обработки данных в компоненте ChatWindow и не требуют изменений на бэкенде.

## Глоссарий

- **Bug_Condition (C)**: Условие, при котором проявляется баг
  - Баг 1: Сообщение с sender_type='admin' приходит через WebSocket
  - Баг 2: Страница перезагружается с существующими сообщениями в истории
- **Property (P)**: Желаемое поведение для входных данных, удовлетворяющих условию бага
  - Баг 1: Сообщения от администратора отображаются справа с синим фоном
  - Баг 2: Каждая уникальная дата имеет только один разделитель
- **Preservation**: Существующее поведение, которое должно остаться неизменным
  - Отображение сообщений от пользователей и ботов
  - Форматирование времени и дат
  - Автоскролл и пагинация
- **sender_type**: Поле в WebSocket сообщении, указывающее тип отправителя ('user', 'admin', 'bot')
- **message_type**: Поле в SupportMessage, определяющее визуальное отображение ('from_user', 'from_support', 'from_bot')
- **groupMessagesByDate**: Функция в ChatWindow.tsx (строка 363), группирующая сообщения по датам для отображения разделителей

## Детали бага

### Баг 1: Неправильное отображение отправителя

#### Условие проявления бага

Баг проявляется при получении сообщения от администратора через WebSocket. В строках 79-88 компонента ChatWindow.tsx происходит преобразование данных WebSocket в объект SupportMessage:

```typescript
const message: SupportMessage = {
  id: serverMessage.data.id,
  session_id: serverMessage.data.session_id,
  telegram_id: session.telegram_id,
  message_type: serverMessage.data.sender_type === 'user' ? 'from_user' : 'from_support',
  message_text: serverMessage.data.message_text,
  created_at: serverMessage.data.created_at,
  delivered: serverMessage.data.is_read || false,
};
```

**Проблема**: Логика преобразования использует бинарное условие, которое не учитывает все возможные значения sender_type. Когда sender_type='admin', условие `sender_type === 'user'` возвращает false, и message_type устанавливается в 'from_support', что корректно. Однако при sender_type='bot' также устанавливается 'from_support', что неверно.

**Формальная спецификация:**
```
FUNCTION isBugCondition1(message)
  INPUT: message типа WebSocketMessage
  OUTPUT: boolean
  
  RETURN message.data.sender_type = 'admin' OR message.data.sender_type = 'bot'
END FUNCTION
```

#### Примеры проявления

**Пример 1: Сообщение администратора**
```typescript
// Входные данные WebSocket
{
  type: 'new_message',
  data: {
    id: 123,
    sender_type: 'admin',  // <- Администратор
    message_text: 'Здравствуйте!'
  }
}

// Текущее поведение: message_type = 'from_support' ✓ (корректно)
// Ожидаемое: message_type = 'from_support' ✓
```

**Пример 2: Сообщение бота**
```typescript
// Входные данные WebSocket
{
  type: 'new_message',
  data: {
    id: 124,
    sender_type: 'bot',  // <- Бот
    message_text: 'Автоматический ответ'
  }
}

// Текущее поведение: message_type = 'from_support' ✗ (неверно)
// Ожидаемое: message_type = 'from_bot' ✓
```

**Пример 3: Сообщение пользователя**
```typescript
// Входные данные WebSocket
{
  type: 'new_message',

    id: 125,

    message_text: 'Помогите!'
  }

// Текущее поведение: message_type = 'from_user' ✓ (корректно)
```

### Баг 2: Дублирование разделителей дат

#### Условие проявления бага

Баг проявляется в функции groupMessagesByDate (строки 363-381) при группировке сообщений после перезагрузки страницы.

```typescript
const groupMessagesByDate = (messages: SupportMessage[]) => {
  const groups: { date: string; messages: SupportMessage[] }[] = [];
  let currentDate = '';

  messages.forEach((message) => {
    const messageDate = new Date(message.created_at).toDateString();

    if (messageDate !== currentDate) {
      currentDate = messageDate;
      groups.push({
        date: formatDate(message.created_at),
        messages: [message],
      });
    } else {
      groups[groups.length - 1].messages.push(message);
    }
  });

  return groups;
};
```

**Проблема**: Функция использует переменную currentDate для отслеживания текущей даты, но инициализирует её пустой строкой. При первой итерации условие `messageDate !== currentDate` всегда истинно (так как '' !== 'Wed Mar 06 2024'), что создаёт первую группу. Однако если сообщения приходят не в строгом хронологическом порядке или если есть временные зоны, могут создаваться дублирующиеся группы.

**Более серьёзная проблема**: Функция сравнивает строковые представления дат (toDateString()), но не учитывает, что сообщения могут быть отсортированы неправильно или могут иметь одинаковую дату, но разное время. Это приводит к созданию нескольких групп для одной даты.

**Формальная спецификация:**
```
FUNCTION isBugCondition2(state)
  INPUT: state типа ChatState (содержит messages и isReloaded)
  OUTPUT: boolean
  
  RETURN state.isReloaded = true 
         AND length(state.messages) > 0
         AND existsDuplicateDateGroups(groupMessagesByDate(state.messages))
END FUNCTION

FUNCTION existsDuplicateDateGroups(groups)
  dates ← extractDates(groups)
  RETURN length(dates) != length(unique(dates))
END FUNCTION
```

#### Примеры проявления

**Пример 1: Дублирование "Сегодня"**
```typescript
// Входные данные
const messages = [
  { id: 1, created_at: '2024-03-06T10:00:00Z', message_text: 'Сообщение 1' },
  { id: 2, created_at: '2024-03-06T11:00:00Z', message_text: 'Сообщение 2' },
  { id: 3, created_at: '2024-03-06T15:00:00Z', message_text: 'Сообщение 3' },
];

// Текущее поведение (после перезагрузки):
// Группа 1: "Сегодня" -> [Сообщение 1, Сообщение 2]
// Группа 2: "Сегодня" -> [Сообщение 3]  ✗ (дубликат)

// Ожидаемое:
// Группа 1: "Сегодня" -> [Сообщение 1, Сообщение 2, Сообщение 3] ✓
```

**Пример 2: Корректная группировка разных дат**
```typescript
// Входные данные
const messages = [
  { id: 1, created_at: '2024-03-05T10:00:00Z', message_text: 'Вчера' },
  { id: 2, created_at: '2024-03-06T11:00:00Z', message_text: 'Сегодня 1' },
  { id: 3, created_at: '2024-03-06T15:00:00Z', message_text: 'Сегодня 2' },
];

// Ожидаемое:
// Группа 1: "Вчера" -> [Вчера]
// Группа 2: "Сегодня" -> [Сегодня 1, Сегодня 2] ✓
```

## Ожидаемое поведение

### Требования к сохранению

**Неизменное поведение:**
- Сообщения от пользователей отображаются слева с белым фоном и тенью
- Сообщения от ботов отображаются с фиолетовым фоном (bg-purple-100) и меткой "🤖 Бот"
- Сортировка сообщений по времени создания (created_at) в порядке возрастания
- Автоскролл к новым сообщениям при их получении через WebSocket
- Форматирование разделителей дат: "Сегодня", "Вчера", "ДД.ММ.ГГГГ"
- Индикаторы доставки (✓ и ✓✓) для сообщений от поддержки
- Пагинация и загрузка истории при скролле вверх

**Область действия:**
Все входные данные, которые НЕ удовлетворяют условиям бага, должны обрабатываться абсолютно идентично до и после исправления. Это включает:
- Сообщения от пользователей (sender_type='user')
- Корректно отформатированные сообщения от администраторов, загруженные из базы данных
- Группировку сообщений при первой загрузке (без перезагрузки)
- Все остальные функции компонента (отправка, подключение, скролл)

## Гипотеза первопричины

На основе анализа кода выявлены следующие первопричины:

### Баг 1: Неполная логика преобразования типов

**Первопричина**: В строке 83 используется тернарный оператор с бинарным условием:
```typescript
message_type: serverMessage.data.sender_type === 'user' ? 'from_user' : 'from_support',
```

Эта логика предполагает только два возможных значения sender_type ('user' и не-'user'), но в системе существует три типа: 'user', 'admin', 'bot'. При получении сообщения с sender_type='bot' через WebSocket, оно неправильно классифицируется как 'from_support'.

**Почему это происходит**:
1. API endpoint `/api/support/sessions/${session.id}/messages` возвращает сообщения с правильным message_type из базы данных
2. WebSocket уведомления приходят с полем sender_type, которое нужно преобразовать в message_type
3. Логика преобразования не учитывает все возможные значения sender_type

### Баг 2: Некорректная логика группировки дат

**Первопричина**: Функция groupMessagesByDate использует последовательное сравнение дат без учёта возможности повторения:

```typescript
let currentDate = '';
messages.forEach((message) => {
  const messageDate = new Date(message.created_at).toDateString();
  if (messageDate !== currentDate) {
    currentDate = messageDate;
    groups.push({ date: formatDate(message.created_at), messages: [message] });
  } else {
    groups[groups.length - 1].messages.push(message);
  }
});
```

**Почему это происходит**:
1. Функция предполагает, что сообщения всегда идут в строгом хронологическом порядке
2. При перезагрузке страницы или при добавлении новых сообщений через WebSocket порядок может нарушаться
3. Если сообщения с одинаковой датой разделены сообщениями с другой датой (из-за асинхронной загрузки), создаются дублирующиеся группы
4. Инициализация currentDate пустой строкой гарантирует создание первой группы, но не предотвращает дубликаты

**Альтернативная гипотеза**: Возможно, проблема связана с тем, что при добавлении новых сообщений через WebSocket они добавляются в конец массива, но их дата может совпадать с уже существующей группой. В этом случае создаётся новая группа вместо добавления в существующую.

## Свойства корректности

Property 1: Fault Condition - Корректное отображение сообщений от администратора

_For any_ WebSocket сообщение, где sender_type='admin', исправленная функция преобразования ДОЛЖНА установить message_type='from_support', что приведёт к отображению сообщения справа с синим фоном (bg-blue-600) и белым текстом.

**Validates: Requirements 2.1, 2.2, 2.3**

Property 2: Fault Condition - Корректное отображение сообщений от бота

_For any_ WebSocket сообщение, где sender_type='bot', исправленная функция преобразования ДОЛЖНА установить message_type='from_bot', что приведёт к отображению сообщения с фиолетовым фоном (bg-purple-100) и меткой "🤖 Бот".

**Validates: Requirements 2.3**

Property 3: Fault Condition - Уникальные разделители дат

_For any_ состояние чата после перезагрузки страницы с существующими сообщениями, исправленная функция группировки ДОЛЖНА создавать только один разделитель для каждой уникальной даты, группируя все сообщения этой даты в один визуальный блок.

**Validates: Requirements 2.4, 2.5, 2.6**

Property 4: Preservation - Неизменное отображение сообщений пользователя

_For any_ WebSocket сообщение, где sender_type='user', исправленная функция преобразования ДОЛЖНА производить тот же результат, что и оригинальная функция, устанавливая message_type='from_user' и отображая сообщение слева с белым фоном.

**Validates: Requirements 3.1**

Property 5: Preservation - Неизменное форматирование и функциональность

_For any_ операция, не связанная с преобразованием типов отправителя или группировкой по датам, исправленный код ДОЛЖЕН производить идентичный результат оригинальному коду, сохраняя форматирование времени, автоскролл, пагинацию и индикаторы доставки.

**Validates: Requirements 3.2, 3.3, 3.4, 3.5, 3.6, 3.7**

## Реализация исправления

### Необходимые изменения

Предполагая, что наш анализ первопричин корректен:

**Файл**: `nextjs-app/components/admin/ChatWindow.tsx`

**Функция**: WebSocket subscription callback (строки 79-88)

**Конкретные изменения**:

1. **Исправление преобразования типов отправителя**:
   - Заменить бинарный тернарный оператор на полное условие switch/if-else
   - Явно обрабатывать все три типа: 'user', 'admin', 'bot'
   - Преобразовывать 'admin' в 'from_support'
   - Преобразовывать 'bot' в 'from_bot'
   - Преобразовывать 'user' в 'from_user'

   ```typescript
   // Было:
   message_type: serverMessage.data.sender_type === 'user' ? 'from_user' : 'from_support',
   
   // Станет:
   message_type: 
     serverMessage.data.sender_type === 'user' ? 'from_user' :
     serverMessage.data.sender_type === 'bot' ? 'from_bot' :
     'from_support',
   ```

2. **Исправление группировки по датам**:
   - Изменить логику функции groupMessagesByDate для использования Map или объекта для отслеживания уже созданных групп
   - Вместо последовательного сравнения использовать поиск существующей группы по дате
   - Если группа для даты уже существует, добавлять сообщение в неё
   - Если группы нет, создавать новую

   ```typescript
   // Было:
   const groupMessagesByDate = (messages: SupportMessage[]) => {
     const groups: { date: string; messages: SupportMessage[] }[] = [];
     let currentDate = '';
     messages.forEach((message) => {
       const messageDate = new Date(message.created_at).toDateString();
       if (messageDate !== currentDate) {
         currentDate = messageDate;
         groups.push({ date: formatDate(message.created_at), messages: [message] });
       } else {
         groups[groups.length - 1].messages.push(message);
       }
     });
     return groups;
   };
   
   // Станет:
   const groupMessagesByDate = (messages: SupportMessage[]) => {
     const groupsMap = new Map<string, { date: string; messages: SupportMessage[] }>();
     
     messages.forEach((message) => {
       const messageDate = new Date(message.created_at).toDateString();
       const formattedDate = formatDate(message.created_at);
       
       if (!groupsMap.has(messageDate)) {
         groupsMap.set(messageDate, { date: formattedDate, messages: [] });
       }
       
       groupsMap.get(messageDate)!.messages.push(message);
     });
     
     return Array.from(groupsMap.values());
   };
   ```

3. **Добавление комментариев**:
   - Добавить комментарии, объясняющие логику преобразования типов
   - Добавить комментарии о том, почему используется Map для группировки

4. **Проверка типов**:
   - Убедиться, что все возможные значения sender_type обрабатываются
   - Добавить fallback для неизвестных типов (по умолчанию 'from_support')

5. **Тестирование**:

## Стратегия тестирования

### Подход к валидации

Стратегия тестирования следует двухфазному подходу: сначала выявить контрпримеры, демонстрирующие баги на неисправленном коде, затем проверить, что исправление работает корректно и сохраняет существующее поведение.

### Исследовательская проверка условий бага

**Цель**: Выявить контрпримеры, демонстрирующие баги ДО реализации исправления. Подтвердить или опровергнуть анализ первопричин. Если опровергнем, потребуется пересмотр гипотез.

**План тестирования**: Написать тесты, симулирующие получение WebSocket сообщений с разными типами отправителей и проверяющие корректность преобразования. Написать тесты, проверяющие группировку сообщений по датам после перезагрузки. Запустить эти тесты на НЕИСПРАВЛЕННОМ коде для наблюдения сбоев и понимания первопричин.

**Тестовые случаи**:
1. **Тест сообщения администратора**: Симулировать WebSocket событие с sender_type='admin' (может пройти на неисправленном коде, если логика случайно корректна)
2. **Тест сообщения бота**: Симулировать WebSocket событие с sender_type='bot' (провалится на неисправленном коде - message_type будет 'from_support' вместо 'from_bot')
3. **Тест дублирования разделителей**: Загрузить сообщения одной даты и проверить количество разделителей (провалится на неисправленном коде - будет несколько разделителей "Сегодня")
4. **Тест группировки разных дат**: Загрузить сообщения разных дат и проверить корректность группировки (должен пройти на неисправленном коде)

**Ожидаемые контрпримеры**:
- Сообщения с sender_type='bot' преобразуются в message_type='from_support' вместо 'from_bot'
- После перезагрузки страницы создаются дублирующиеся разделители для одной даты
- Возможные причины: неполная логика преобразования типов, последовательное сравнение дат без учёта дубликатов

### Проверка исправления

**Цель**: Проверить, что для всех входных данных, удовлетворяющих условию бага, исправленная функция производит ожидаемое поведение.

**Псевдокод:**
```
FOR ALL message WHERE isBugCondition1(message) DO
  result := transformMessage_fixed(message)
  ASSERT expectedBehavior1(result)
END FOR

FOR ALL state WHERE isBugCondition2(state) DO
  groups := groupMessagesByDate_fixed(state.messages)
  ASSERT expectedBehavior2(groups)
END FOR
```

### Проверка сохранения

**Цель**: Проверить, что для всех входных данных, НЕ удовлетворяющих условию бага, исправленная функция производит тот же результат, что и оригинальная.

**Псевдокод:**
```
FOR ALL message WHERE NOT isBugCondition1(message) DO
  ASSERT transformMessage_original(message) = transformMessage_fixed(message)
END FOR

FOR ALL state WHERE NOT isBugCondition2(state) DO
  ASSERT groupMessagesByDate_original(state.messages) = groupMessagesByDate_fixed(state.messages)
END FOR
```

**Подход к тестированию**: Property-based тестирование рекомендуется для проверки сохранения, потому что:
- Автоматически генерирует множество тестовых случаев по всему входному домену
- Выявляет граничные случаи, которые могут быть пропущены в ручных unit-тестах
- Предоставляет сильные гарантии, что поведение не изменилось для всех не-багованных входных данных

**План тестирования**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для сообщений от пользователей и корректной группировки, затем написать property-based тесты, фиксирующие это поведение.

**Тестовые случаи**:
1. **Сохранение отображения сообщений пользователя**: Наблюдать, что сообщения с sender_type='user' отображаются слева с белым фоном на неисправленном коде, затем написать тест для проверки сохранения после исправления
2. **Сохранение форматирования времени**: Проверить, что функция formatTime работает идентично до и после исправления
3. **Сохранение автоскролла**: Проверить, что автоскролл к новым сообщениям работает корректно после исправления
4. **Сохранение пагинации**: Проверить, что загрузка истории при скролле вверх работает идентично

### Unit-тесты

- Тест преобразования sender_type='user' в message_type='from_user'
- Тест преобразования sender_type='admin' в message_type='from_support'
- Тест преобразования sender_type='bot' в message_type='from_bot'
- Тест группировки сообщений одной даты в одну группу
- Тест группировки сообщений разных дат в разные группы
- Тест граничных случаев (пустой массив сообщений, одно сообщение)

### Property-Based тесты

- Генерировать случайные WebSocket сообщения с разными sender_type и проверять корректность преобразования
- Генерировать случайные наборы сообщений с разными датами и проверять уникальность разделителей
- Тестировать, что все сообщения от пользователей продолжают отображаться корректно в различных сценариях
- Проверять инвариант: количество уникальных дат = количество групп

### Интеграционные тесты

- Тест полного потока: загрузка истории, получение нового сообщения от администратора через WebSocket, проверка корректного отображения
- Тест перезагрузки страницы: загрузка сообщений, перезагрузка, проверка отсутствия дублирующихся разделителей
- Тест переключения между сессиями: открытие разных чатов и проверка корректной группировки в каждом
- Тест визуального отображения: проверка, что сообщения от администратора отображаются справа с синим фоном, а от пользователя - слева с белым
