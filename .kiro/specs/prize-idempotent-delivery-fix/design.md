# Дизайн исправления бага идемпотентной выдачи призов

## Overview

Исправление бага в методе `check_user_exists` в `prize_repository.py`, который проверяет только призы с `claimed_at IS NULL`, из-за чего при повторном запросе приза система некорректно считает, что пользователя нет в списке победителей. Это приводит к показу ошибки "У вас нет доступных призов" вместо идемпотентной выдачи промокода (для цифровых призов) или показа статуса заполненной формы (для физических призов).

Исправление обеспечит идемпотентность операции получения приза: повторные запросы с правильным кодовым словом будут возвращать тот же результат без ошибок.

## Glossary

- **Bug_Condition (C)**: Условие, при котором проявляется баг - когда пользователь с уже полученным призом (`claimed_at IS NOT NULL`) запрашивает приз повторно
- **Property (P)**: Желаемое поведение для C(X) - идемпотентная выдача промокода для цифровых призов или показ статуса заполненной формы для физических призов
- **Preservation**: Существующее поведение первичной выдачи призов и обработки несуществующих пользователей, которое должно остаться неизменным
- **check_user_exists**: Метод в `prize_repository.py` (строки 453-505), который проверяет наличие пользователя в таблице призов
- **claimed_at**: Timestamp в таблице `prizes`, указывающий время получения приза (NULL = не получен, NOT NULL = получен)
- **Идемпотентность**: Свойство операции, при котором повторное выполнение с теми же параметрами дает тот же результат

## Bug Details

### Bug Condition

Баг проявляется когда пользователь, уже получивший приз (цифровой или физический), нажимает кнопку "Получить приз" повторно. Метод `check_user_exists` в `prize_repository.py` проверяет только записи с `claimed_at IS NULL`, что приводит к ложному результату "пользователь не найден" для уже полученных призов.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type { telegram_id: int, action: string }
  OUTPUT: boolean
  
  RETURN input.action == "get_prize"
         AND userExistsInPrizesTable(input.telegram_id)
         AND userPrizeClaimedAt(input.telegram_id) IS NOT NULL
         AND check_user_exists(input.telegram_id) returns False
END FUNCTION
```

### Examples

- **Цифровой приз (промокод)**: Пользователь с telegram_id=123456 получил промокод "PROMO2024" (claimed_at установлен). При повторном нажатии "Получить приз" система показывает "❌ У вас нет доступных призов" вместо повторной выдачи промокода "PROMO2024"

- **Физический приз (заполненная форма)**: Пользователь с telegram_id=789012 заполнил форму доставки (claimed_at установлен). При повторном запросе с правильным кодовым словом система показывает "❌ У вас нет доступных призов" вместо сообщения "✅ Вы уже заполнили данные для получения приза" с кнопками действий

- **Физический приз (незаполненная форма)**: Пользователь с telegram_id=345678 ввел правильное кодовое слово, но не заполнил форму доставки (claimed_at IS NULL). При повторном запросе система корректно показывает форму доставки (это работает правильно)

- **Несуществующий пользователь**: Пользователь с telegram_id=999999 отсутствует в таблице призов. Система корректно показывает "❌ У вас нет доступных призов" (это должно остаться неизменным)

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Первичная выдача призов (когда пользователь запрашивает приз впервые) должна продолжать работать точно так же
- Обработка несуществующих пользователей (не в списке победителей) должна продолжать показывать сообщение "У вас нет доступных призов"
- Валидация кодового слова должна продолжать работать для всех случаев (правильное/неправильное кодовое слово)
- Установка `claimed_at` для цифровых призов при первой выдаче промокода должна продолжать работать
- Установка `claimed_at` для физических призов после заполнения формы доставки должна продолжать работать
- Запрос GDPR согласия для пользователей без согласия должен продолжать работать
- Показ формы доставки через WebApp для физических призов при первом запросе должен продолжать работать

**Scope:**
Все входные данные, которые НЕ относятся к повторному запросу уже полученного приза, должны быть полностью не затронуты этим исправлением. Это включает:
- Первичные запросы призов (пользователь запрашивает приз впервые)
- Запросы от несуществующих пользователей (не в списке победителей)
- Неправильные кодовые слова
- Запросы без GDPR согласия

## Hypothesized Root Cause

На основе анализа кода, наиболее вероятные причины бага:

1. **Некорректный SQL-запрос в check_user_exists**: Метод использует условие `Prize.claimed_at.is_(None)` в WHERE-клаузе, что исключает из поиска все записи с установленным `claimed_at`. Это приводит к тому, что пользователи с уже полученными призами не находятся в таблице.

2. **Неправильная семантика метода**: Название метода `check_user_exists` подразумевает проверку существования пользователя в таблице призов, но фактически он проверяет наличие "неполученных призов". Это несоответствие между названием и реализацией привело к неправильному использованию метода.

3. **Отсутствие проверки идемпотентности на уровне бизнес-логики**: В методе `start_prize_flow` в `prize_flow_handler.py` используется `check_user_exists` для определения, может ли пользователь начать процесс получения приза. Но этот метод не учитывает случай повторного запроса уже полученного приза.

4. **Логика в _check_prize_postgres не учитывает повторные запросы**: Метод `_check_prize_postgres` в `prize_service.py` корректно находит приз по кодовому слову независимо от `claimed_at`, но до него не доходит выполнение, так как `check_user_exists` уже вернул False на этапе `start_prize_flow`.

## Correctness Properties

Property 1: Bug Condition - Идемпотентная проверка существования пользователя

_For any_ пользователя, который существует в таблице призов (независимо от значения `claimed_at`), исправленный метод `check_user_exists` SHALL возвращать True, позволяя пользователю продолжить процесс получения приза.

**Validates: Requirements 2.1, 2.4**

Property 2: Bug Condition - Идемпотентная выдача цифровых призов

_For any_ пользователя с уже полученным цифровым призом (claimed_at IS NOT NULL), который вводит правильное кодовое слово, исправленная система SHALL идемпотентно вернуть тот же промокод с инструкциями, не изменяя состояние в базе данных.

**Validates: Requirements 2.2**

Property 3: Bug Condition - Показ статуса заполненной формы для физических призов

_For any_ пользователя с уже заполненной формой доставки для физического приза (claimed_at IS NOT NULL), который вводит правильное кодовое слово, исправленная система SHALL показать сообщение "✅ Вы уже заполнили данные для получения приза" с inline клавиатурой, содержащей кнопки "◀️ Назад" и "✏️ Изменить данные".

**Validates: Requirements 2.3**

Property 4: Preservation - Первичная выдача призов

_For any_ пользователя, который запрашивает приз впервые (claimed_at IS NULL для цифровых призов или до заполнения формы для физических), исправленная система SHALL продолжать выдавать промокод для цифровых призов или показывать форму доставки для физических призов точно так же, как до исправления.

**Validates: Requirements 3.1, 3.7**

Property 5: Preservation - Обработка несуществующих пользователей

_For any_ пользователя, который отсутствует в таблице призов (не является победителем), исправленная система SHALL продолжать показывать сообщение "❌ У вас нет доступных призов" точно так же, как до исправления.

**Validates: Requirements 3.2**

Property 6: Preservation - Валидация кодового слова

_For any_ пользователя, который вводит неправильное кодовое слово, исправленная система SHALL продолжать показывать сообщение "❌ Кодовое слово введено неверно" точно так же, как до исправления.

**Validates: Requirements 2.5, 3.3**

Property 7: Preservation - Установка claimed_at

_For any_ пользователя, который получает приз впервые, исправленная система SHALL продолжать устанавливать timestamp в `claimed_at` при первой выдаче цифрового приза или после заполнения формы доставки для физического приза точно так же, как до исправления.

**Validates: Requirements 3.4, 3.5**

Property 8: Preservation - GDPR согласие

_For any_ пользователя, который не дал GDPR согласие, исправленная система SHALL продолжать запрашивать согласие перед запросом кодового слова точно так же, как до исправления.

**Validates: Requirements 3.6**

## Fix Implementation

### Changes Required

Предполагая, что наш анализ корректен:

**File**: `telegram-bot/database/repositories/prize_repository.py`

**Function**: `check_user_exists` (строки 453-505)

**Specific Changes**:
1. **Удалить условие claimed_at из SQL-запроса**: Убрать `Prize.claimed_at.is_(None)` из WHERE-клаузы, чтобы метод искал пользователя в таблице призов независимо от статуса получения приза
   - Было: `Prize.telegram_id == telegram_id, Prize.claimed_at.is_(None)`
   - Станет: `Prize.telegram_id == telegram_id`

2. **Обновить docstring метода**: Изменить описание метода, чтобы оно отражало новую семантику - проверка существования пользователя в таблице призов (а не проверка наличия неполученных призов)
   - Было: "Проверяет наличие пользователя с неполученными призами в таблице призов"
   - Станет: "Проверяет наличие пользователя в таблице призов независимо от статуса получения приза"

3. **Обновить комментарии в коде**: Удалить или изменить комментарий "claimed_at IS NULL означает, что приз еще не получен", так как теперь мы не фильтруем по этому условию

4. **Обновить логирование**: Изменить сообщения логирования, чтобы они отражали новую логику (проверка существования, а не проверка неполученных призов)

**File**: `telegram-bot/services/prize_service.py`

**Function**: `check_user_exists` (строки 71-103)

**Specific Changes**:
1. **Обновить docstring метода**: Изменить описание, чтобы оно соответствовало новой семантике метода в репозитории
   - Было: "Проверяет наличие пользователя в таблице призов"
   - Уточнить: "Проверяет наличие пользователя в таблице призов независимо от статуса получения приза (claimed_at)"

**File**: `telegram-bot/handlers/prize_flow_handler.py`

**Function**: `handle_code_word_input` (строки 693-800+)

**Specific Changes**:
1. **Добавить обработку уже заполненной формы доставки**: После проверки `is_delivery_filled`, если форма заполнена, отправить сообщение `DELIVERY_DATA_ALREADY_FILLED` с клавиатурой `get_delivery_actions_keyboard`
   - Использовать существующую константу `DELIVERY_DATA_ALREADY_FILLED` из `constants/messages.py`
   - Использовать существующую функцию `get_delivery_actions_keyboard(prize_id, webapp_url)` из `keyboards/reply_keyboards.py`
   - Сбросить состояние FSM после отправки сообщения

2. **Обеспечить идемпотентность для цифровых призов**: Метод `_check_prize_postgres` уже корректно обрабатывает повторные запросы цифровых призов (находит приз и возвращает промокод), но не устанавливает `claimed_at` повторно. Нужно убедиться, что `_mark_prize_claimed_async` не вызывается для уже полученных призов.

## Testing Strategy

### Validation Approach

Стратегия тестирования следует двухфазному подходу: сначала выявить контрпримеры, демонстрирующие баг на неисправленном коде, затем проверить, что исправление работает корректно и сохраняет существующее поведение.

### Exploratory Bug Condition Checking

**Goal**: Выявить контрпримеры, демонстрирующие баг ДО внедрения исправления. Подтвердить или опровергнуть анализ корневой причины. Если опровергнем, потребуется пересмотреть гипотезу.

**Test Plan**: Написать тесты, которые симулируют повторные запросы призов для пользователей с уже установленным `claimed_at`. Запустить эти тесты на НЕИСПРАВЛЕННОМ коде, чтобы наблюдать сбои и понять корневую причину.

**Test Cases**:
1. **Повторный запрос цифрового приза**: Создать пользователя с полученным цифровым призом (claimed_at установлен), вызвать `check_user_exists` (будет возвращать False на неисправленном коде)
2. **Повторный запрос физического приза с заполненной формой**: Создать пользователя с заполненной формой доставки (claimed_at установлен), вызвать `check_user_exists` (будет возвращать False на неисправленном коде)
3. **Повторный ввод кодового слова для цифрового приза**: Симулировать полный flow с повторным вводом правильного кодового слова для уже полученного цифрового приза (будет показывать ошибку "У вас нет доступных призов" на неисправленном коде)
4. **Повторный ввод кодового слова для физического приза**: Симулировать полный flow с повторным вводом правильного кодового слова для физического приза с заполненной формой (будет показывать ошибку "У вас нет доступных призов" на неисправленном коде)

**Expected Counterexamples**:
- `check_user_exists` возвращает False для пользователей с `claimed_at IS NOT NULL`
- Система показывает "❌ У вас нет доступных призов" вместо идемпотентной выдачи промокода или показа статуса формы
- Возможные причины: SQL-запрос с условием `claimed_at IS NULL`, неправильная семантика метода

### Fix Checking

**Goal**: Проверить, что для всех входных данных, где выполняется условие бага, исправленная функция производит ожидаемое поведение.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := check_user_exists_fixed(input.telegram_id)
  ASSERT result == True
  
  IF input.prize_type == "digital" THEN
    prize_result := check_prize_fixed(input.telegram_id, input.code_word)
    ASSERT prize_result.status == PrizeStatus.DIGITAL
    ASSERT prize_result.promo_code == input.expected_promo_code
  END IF
  
  IF input.prize_type == "physical" AND input.delivery_filled THEN
    response := handle_code_word_input_fixed(input.telegram_id, input.code_word)
    ASSERT response.message == DELIVERY_DATA_ALREADY_FILLED
    ASSERT response.keyboard == get_delivery_actions_keyboard(...)
  END IF
END FOR
```

### Preservation Checking

**Goal**: Проверить, что для всех входных данных, где условие бага НЕ выполняется, исправленная функция производит тот же результат, что и оригинальная функция.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT check_user_exists_original(input) == check_user_exists_fixed(input)
  ASSERT check_prize_original(input) == check_prize_fixed(input)
  ASSERT handle_code_word_input_original(input) == handle_code_word_input_fixed(input)
END FOR
```

**Testing Approach**: Property-based testing рекомендуется для preservation checking, потому что:
- Автоматически генерирует множество тестовых случаев по всему домену входных данных
- Выявляет граничные случаи, которые могут быть пропущены в ручных unit-тестах
- Предоставляет сильные гарантии, что поведение не изменилось для всех входных данных, не относящихся к багу

**Test Plan**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для первичных запросов призов и несуществующих пользователей, затем написать property-based тесты, фиксирующие это поведение.

**Test Cases**:
1. **Preservation первичной выдачи цифровых призов**: Наблюдать, что первичная выдача промокода работает на неисправленном коде, затем написать тест для проверки, что это продолжает работать после исправления
2. **Preservation первичной выдачи физических призов**: Наблюдать, что показ формы доставки работает на неисправленном коде, затем написать тест для проверки, что это продолжает работать после исправления
3. **Preservation обработки несуществующих пользователей**: Наблюдать, что сообщение "У вас нет доступных призов" показывается для несуществующих пользователей на неисправленном коде, затем написать тест для проверки, что это продолжает работать после исправления
4. **Preservation валидации кодового слова**: Наблюдать, что неправильные кодовые слова отклоняются на неисправленном коде, затем написать тест для проверки, что это продолжает работать после исправления

### Unit Tests

- Тест метода `check_user_exists` с пользователями, имеющими `claimed_at IS NULL` (должен возвращать True)
- Тест метода `check_user_exists` с пользователями, имеющими `claimed_at IS NOT NULL` (должен возвращать True после исправления)
- Тест метода `check_user_exists` с несуществующими пользователями (должен возвращать False)
- Тест повторной выдачи цифрового приза (должен возвращать тот же промокод)

### Property-Based Tests

- Генерировать случайные состояния пользователей (с различными значениями `claimed_at`) и проверять, что `check_user_exists` возвращает True для всех существующих пользователей

- Генерировать случайные первичные запросы призов и проверять, что поведение не изменилось (preservation)
- Тестировать, что повторные вызовы с одинаковыми параметрами возвращают одинаковые результаты (идемпотентность)

### Integration Tests

- Полный flow повторного получения цифрового приза: нажатие "Получить приз" → ввод кодового слова → получение промокода
- Полный flow повторного запроса физического приза с заполненной формой: нажатие "Получить приз" → ввод кодового слова → показ сообщения с кнопками действий
- Полный flow первичного получения приза для проверки preservation
- Тестирование переключения между различными состояниями FSM при повторных запросах
