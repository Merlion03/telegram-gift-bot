# Bugfix Requirements Document

## Введение

Исправление критического бага с доставкой real-time сообщений через WebSocket в чате. Сообщения, отправленные боту в Telegram, записываются в базу данных и триггер PostgreSQL отправляет уведомление через pg_notify, но эти уведомления не доставляются на фронтенд по WebSocket. Пользователь вынужден обновлять страницу (F5) для отображения новых сообщений.

**Стек технологий:**
- Backend: Next.js с кастомным WebSocket сервером
- Database: PostgreSQL с LISTEN/NOTIFY механизмом
- Bot: Telegram Bot (aiogram)
- Frontend: React

**Локализация проблемы:**
Триггер `notify_new_message()` отправляет уведомления в канал `new_message`, но `NotificationRouter` не обрабатывает этот канал. Router ожидает каналы `all_messages` или `session_*`, что приводит к потере всех уведомлений о новых сообщениях.

## Анализ бага

### Текущее поведение (Дефект)

1.1 КОГДА триггер `notify_new_message()` отправляет уведомление в канал `new_message` после INSERT в таблицу `support_messages` ТО система не доставляет это уведомление клиентам, подписанным на канал `session_*`

1.2 КОГДА `NotificationRouter.createMessageFromPayload()` получает уведомление с каналом `new_message` ТО метод возвращает `null` и логирует предупреждение "Неизвестный канал: new_message"

1.3 КОГДА пользователь отправляет сообщение боту в Telegram ТО сообщение записывается в БД, но не появляется в веб-интерфейсе чата в реальном времени

1.4 КОГДА клиент подписывается на канал `session` с `sessionId: 2` ТО сервер регистрирует подписку на канал `session_2`, но уведомления из канала `new_message` не маршрутизируются к этой подписке

### Ожидаемое поведение (Корректное)

2.1 КОГДА триггер `notify_new_message()` отправляет уведомление в канал `new_message` с `session_id` в payload ТО система ДОЛЖНА доставить это уведомление всем клиентам, подписанным на соответствующий канал `session_*`

2.2 КОГДА `NotificationRouter.createMessageFromPayload()` получает уведомление с каналом `new_message` ТО метод ДОЛЖЕН распарсить payload, извлечь `session_id` и создать корректное `NewMessageMessage`

2.3 КОГДА пользователь отправляет сообщение боту в Telegram ТО сообщение ДОЛЖНО немедленно появиться в веб-интерфейсе чата без необходимости обновления страницы

2.4 КОГДА клиент подписан на канал `session_2` и приходит уведомление в канал `new_message` с `session_id: 2` ТО система ДОЛЖНА маршрутизировать это уведомление к подписчику канала `session_2`

### Неизменное поведение (Предотвращение регрессии)

3.1 КОГДА триггер `notify_session_status_change()` отправляет уведомление в канал `session_status_change` ТО система ДОЛЖНА ПРОДОЛЖАТЬ корректно обрабатывать эти уведомления через канал `status_changes`

3.2 КОГДА триггер `notify_session_type_change()` отправляет уведомление в канал `session_type_change` ТО система ДОЛЖНА ПРОДОЛЖАТЬ корректно обрабатывать эти уведомления через канал `type_changes`

3.3 КОГДА клиент подписывается на канал `all` ТО система ДОЛЖНА ПРОДОЛЖАТЬ корректно регистрировать подписку на канал `all_messages`

3.4 КОГДА клиент подписывается на канал `status` ТО система ДОЛЖНА ПРОДОЛЖАТЬ корректно регистрировать подписку на канал `status_changes`

3.5 КОГДА `NotificationRouter` получает уведомление для канала, на который нет подписчиков ТО система ДОЛЖНА ПРОДОЛЖАТЬ логировать информационное сообщение без ошибок

3.6 КОГДА WebSocket соединение установлено и работает heartbeat (ping-pong) ТО система ДОЛЖНА ПРОДОЛЖАТЬ поддерживать стабильное соединение без ошибок 1006

3.7 КОГДА пользователь обновляет страницу чата (F5) ТО система ДОЛЖНА ПРОДОЛЖАТЬ корректно загружать все сообщения из базы данных
