# Privacy Policy Consent Persistence Bugfix Design

## Overview

Баг проявляется в том, что согласие пользователя с политикой конфиденциальности не сохраняется между перезапусками бота. Текущая реализация хранит согласие в поле `gdpr_consent_date` таблицы `prizes`, что приводит к потере данных для пользователей без призов. Решение заключается в создании отдельной таблицы `gdpr_consents` для независимого хранения согласий.

## Glossary

- **Bug_Condition (C)**: Условие, при котором согласие пользователя теряется - когда у пользователя нет записей в таблице `prizes` или после перезапуска бота
- **Property (P)**: Желаемое поведение - согласие должно сохраняться независимо от наличия призов и сохраняться между перезапусками
- **Preservation**: Существующее поведение запроса согласия для новых пользователей и обработки кнопки "Назад" должно остаться неизменным
- **gdpr_consent_date**: Поле в таблице `prizes`, которое в текущей реализации хранит дату согласия (будет заменено на отдельную таблицу)
- **check_gdpr_consent()**: Метод в `prize_service.py`, который проверяет наличие согласия пользователя
- **save_gdpr_consent()**: Метод в `prize_service.py`, который сохраняет согласие пользователя
- **get_gdpr_consent_date()**: Метод в `prize_repository.py`, который получает дату согласия из БД
- **update_gdpr_consent()**: Метод в `prize_repository.py`, который обновляет дату согласия в БД

## Bug Details

### Bug Condition

Баг проявляется когда пользователь дает согласие с политикой конфиденциальности, но это согласие не может быть найдено при последующих обращениях. Методы `get_gdpr_consent_date()` и `update_gdpr_consent()` в `prize_repository.py` работают только с таблицей `prizes`, что делает согласие зависимым от наличия призов у пользователя.

**Formal Specification:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type UserConsentCheck
  OUTPUT: boolean
  
  RETURN input.user_gave_consent == TRUE
         AND (input.user_has_no_prizes == TRUE 
              OR input.bot_restarted == TRUE)
         AND get_gdpr_consent_date(input.telegram_id) == NULL
END FUNCTION
```

### Examples

- Пользователь дает согласие, нажимая "✅ Согласен", но у него еще нет записей в таблице `prizes` → согласие не может быть сохранено → при следующем обращении запрашивается снова
- Пользователь дал согласие и получил приз, но после перезапуска бота метод `get_gdpr_consent_date()` не находит согласие → запрашивается снова
- Пользователь дал согласие, но метод `update_gdpr_consent()` обновляет только существующие записи в `prizes` → если записей нет, согласие теряется
- Пользователь впервые заходит в бот → согласие должно быть запрошено (корректное поведение, не баг)

## Expected Behavior

### Preservation Requirements

**Unchanged Behaviors:**
- Запрос согласия для новых пользователей, которые еще не давали согласие
- Обработка кнопки "🔙 Назад" - возврат в главное меню без сохранения согласия
- Запрос кодового слова после получения согласия
- Весь флоу проверки приза для пользователей с сохраненным согласием

**Scope:**
Все взаимодействия, которые НЕ связаны с сохранением и проверкой GDPR согласия, должны остаться полностью неизменными. Это включает:
- Обработку кнопки "Назад" на экране согласия
- Валидацию кодового слова
- Выдачу цифровых и физических призов
- Любые другие операции с таблицей `prizes`

## Hypothesized Root Cause

На основе анализа кода, наиболее вероятные причины бага:

1. **Зависимость от таблицы prizes**: Методы `get_gdpr_consent_date()` и `update_gdpr_consent()` работают только с таблицей `prizes`
   - `get_gdpr_consent_date()` выполняет запрос `SELECT gdpr_consent_date FROM prizes WHERE telegram_id = ?`
   - Если у пользователя нет записей в `prizes`, запрос возвращает NULL
   - `update_gdpr_consent()` выполняет `UPDATE prizes SET gdpr_consent_date = ? WHERE telegram_id = ?`
   - Если записей нет, UPDATE не создает новых записей

2. **Отсутствие независимого хранилища**: Согласие GDPR концептуально не связано с призами, но хранится в той же таблице
   - Это нарушает принцип разделения ответственности
   - Создает ненужную зависимость между двумя независимыми сущностями

3. **Проблема с жизненным циклом данных**: Согласие должно существовать независимо от призов
   - Пользователь может дать согласие до получения приза
   - Согласие должно сохраняться даже если все призы будут удалены

4. **Отсутствие миграции данных**: При создании отдельной таблицы потребуется перенести существующие согласия из `prizes`

## Correctness Properties

Property 1: Bug Condition - GDPR Consent Persistence

_For any_ пользователь, который дает согласие с политикой конфиденциальности (нажимает "✅ Согласен"), исправленная система SHALL сохранить это согласие в отдельную таблицу `gdpr_consents` с полями telegram_id и consent_date, и это согласие SHALL быть доступно при всех последующих проверках независимо от наличия призов или перезапусков бота.

**Validates: Requirements 2.1, 2.2, 2.3**

Property 2: Preservation - Existing Consent Flow Behavior

_For any_ взаимодействие пользователя, которое НЕ связано с сохранением или проверкой GDPR согласия (обработка кнопки "Назад", валидация кодового слова, выдача призов), исправленный код SHALL производить точно такой же результат, как и оригинальный код, сохраняя все существующие функциональности без изменений.

**Validates: Requirements 3.1, 3.2, 3.3, 3.4**

## Fix Implementation

### Changes Required

Предполагая, что наш анализ корневой причины верен:

**File**: `telegram-bot/database/models/gdpr_consent.py` (новый файл)

**Changes**:
1. **Создание новой модели GdprConsent**: Определить SQLAlchemy модель для хранения согласий
   - Поля: id (PK), telegram_id (unique, indexed), consent_date, created_at, updated_at
   - Уникальный индекс на telegram_id для предотвращения дублирования
   - Связь с Base классом из `database/models/base.py`

**File**: `telegram-bot/database/repositories/gdpr_consent_repository.py` (новый файл)

**Changes**:
2. **Создание GdprConsentRepository**: Реализовать методы для работы с согласиями
   - `get_consent(telegram_id)` - получить согласие пользователя
   - `save_consent(telegram_id, consent_date)` - сохранить согласие (upsert)
   - `check_consent_exists(telegram_id)` - проверить наличие согласия
   - Наследование от BaseRepository для использования общей логики сессий

**File**: `telegram-bot/services/prize_service.py`

**Function**: `check_gdpr_consent()` и `save_gdpr_consent()`

**Specific Changes**:
3. **Обновление методов в PrizeService**: Переключить на использование GdprConsentRepository
   - В `check_gdpr_consent()`: заменить вызов `prize_repository.get_gdpr_consent_date()` на `gdpr_consent_repository.get_consent()`
   - В `save_gdpr_consent()`: заменить вызов `prize_repository.update_gdpr_consent()` на `gdpr_consent_repository.save_consent()`
   - Добавить инициализацию `gdpr_consent_repository` в конструкторе

**File**: `telegram-bot/database/repositories/prize_repository.py`

**Specific Changes**:
4. **Удаление устаревших методов**: Удалить методы, связанные с GDPR из PrizeRepository
   - Удалить метод `get_gdpr_consent_date()`
   - Удалить метод `update_gdpr_consent()`
   - Эти методы больше не нужны, так как согласие хранится в отдельной таблице

**File**: `telegram-bot/database/models/prize.py`

**Specific Changes**:

   - Создать таблицу `gdpr_consents` с необходимыми полями
   - Перенести существующие данные из `prizes.gdpr_consent_date` в новую таблицу

## Testing Strategy

### Validation Approach

Стратегия тестирования следует двухфазному подходу: сначала выявить контрпримеры, демонстрирующие баг на неисправленном коде, затем проверить, что исправление работает корректно и сохраняет существующее поведение.

### Exploratory Bug Condition Checking

**Goal**: Выявить контрпримеры, демонстрирующие баг ДО реализации исправления. Подтвердить или опровергнуть анализ корневой причины. Если опровергнем, потребуется пересмотреть гипотезу.

**Test Plan**: Написать тесты, которые симулируют сценарии потери согласия и проверяют, что согласие не сохраняется или не находится. Запустить эти тесты на НЕИСПРАВЛЕННОМ коде для наблюдения ошибок и понимания корневой причины.

**Test Cases**:
1. **User Without Prizes Test**: Пользователь дает согласие, но у него нет записей в таблице `prizes` (провалится на неисправленном коде)
2. **Bot Restart Test**: Пользователь дал согласие, бот перезапускается, согласие проверяется снова (провалится на неисправленном коде)
3. **Consent Retrieval Test**: Вызвать `get_gdpr_consent_date()` для пользователя без призов (провалится на неисправленном коде)
4. **Consent Save Without Prize Test**: Вызвать `update_gdpr_consent()` для пользователя без записей в `prizes` (провалится на неисправленном коде)

**Expected Counterexamples**:
- Метод `get_gdpr_consent_date()` возвращает NULL для пользователей без призов, даже если они давали согласие
- Метод `update_gdpr_consent()` не создает новых записей, если у пользователя нет призов
- Возможные причины: зависимость от таблицы `prizes`, отсутствие независимого хранилища, проблемы с UPDATE запросами

### Fix Checking

**Goal**: Проверить, что для всех входных данных, где выполняется условие бага, исправленная функция производит ожидаемое поведение.

**Pseudocode:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := check_gdpr_consent_fixed(input.telegram_id)
  ASSERT result == TRUE (согласие найдено)
  
  consent_data := get_consent_from_db(input.telegram_id)
  ASSERT consent_data.telegram_id == input.telegram_id
  ASSERT consent_data.consent_date IS NOT NULL
END FOR
```

### Preservation Checking

**Goal**: Проверить, что для всех входных данных, где условие бага НЕ выполняется, исправленная функция производит тот же результат, что и оригинальная функция.

**Pseudocode:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT check_gdpr_consent_original(input) = check_gdpr_consent_fixed(input)
  ASSERT save_gdpr_consent_original(input) = save_gdpr_consent_fixed(input)
END FOR
```

**Testing Approach**: Property-based тестирование рекомендуется для preservation checking, потому что:
- Автоматически генерирует множество тестовых случаев по всему домену входных данных
- Выявляет граничные случаи, которые могут быть пропущены в ручных unit тестах
- Предоставляет сильные гарантии, что поведение не изменилось для всех не-багованных входных данных

**Test Plan**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для операций, не связанных с GDPR, затем написать property-based тесты, фиксирующие это поведение.

**Test Cases**:
1. **Back Button Preservation**: Наблюдать, что кнопка "Назад" работает корректно на неисправленном коде, затем написать тест для проверки после исправления
2. **Code Word Validation Preservation**: Наблюдать, что валидация кодового слова работает корректно, затем написать тест для проверки после исправления
3. **Prize Operations Preservation**: Наблюдать, что операции с призами (find_prize, update_delivery_data) работают корректно, затем написать тест для проверки после исправления

### Unit Tests

- Тест создания записи в `gdpr_consents` при первом согласии
- Тест обновления существующей записи при повторном согласии (idempotency)
- Тест получения согласия для пользователя с согласием
- Тест получения NULL для пользователя без согласия
- Тест уникальности telegram_id в таблице `gdpr_consents`
- Тест миграции данных из `prizes.gdpr_consent_date` в `gdpr_consents`

### Property-Based Tests

- Генерировать случайные telegram_id и проверять, что согласие сохраняется и извлекается корректно
- Генерировать случайные сценарии с/без призов и проверять, что согласие работает независимо
- Генерировать случайные последовательности операций (save, check, save, check) и проверять консистентность
- Тестировать, что все операции с призами продолжают работать одинаково до и после исправления

### Integration Tests

- Тест полного флоу: пользователь дает согласие → перезапуск бота → проверка согласия → согласие найдено
- Тест флоу без призов: пользователь без призов дает согласие → согласие сохраняется → согласие находится
- Тест флоу с призами: пользователь с призами дает согласие → согласие сохраняется в обеих таблицах (если оставляем поле в prizes)
- Тест обработки кнопки "Назад" после исправления - должна работать идентично
