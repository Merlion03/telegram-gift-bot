# Bugfix Requirements Document

## Введение

WebSocket соединения закрываются сразу после установки с кодом 1006 (abnormal closure). Проблема проявляется на клиентской стороне: соединение успешно устанавливается (HTTP Upgrade проходит), аутентификация на сервере проходит успешно, но сразу после этого соединение закрывается аномально без нормального close frame.

**Ключевые факты из анализа:**
- Сервер успешно выполняет WebSocket upgrade и аутентификацию (userId: 1, admin, isAdmin: true)
- Код 1006 означает аномальное закрытие без close frame - соединение оборвалось нештатно
- Сервер НИ РАЗУ не получает init сообщение от клиента
- Логи показывают: `hasWs: false, readyState: undefined` в момент попытки отправки init
- Проблема повторяется циклически каждую секунду при переподключении

Из анализа логов выявлена **race condition** в `ConnectionManager.connect()`: после события `open` WebSocket, во время асинхронной задержки 50ms для стабилизации прокси, событие `close` срабатывает раньше, чем успевает отправиться init сообщение. В результате `this.ws` становится `null`, и init сообщение не отправляется (`sent: false`).

**Последовательность событий в багованном коде:**
1. WebSocket открывается → событие `open` → `handleOpen()` начинает выполняться
2. Начинается `await setTimeout(50ms)` для стабилизации прокси
3. **ВО ВРЕМЯ ОЖИДАНИЯ**: WebSocket закрывается → событие `close` → `handleClose()` устанавливает `this.ws = null`
4. После завершения задержки: попытка `this.send(initMessage)` → `this.ws === null` → сообщение не отправляется
5. Сервер не получает init сообщение → соединение остаётся неинициализированным → закрывается

**Корневая причина:** Клиент сам теряет или закрывает WebSocket сразу после успешного подключения из-за race condition в управлении жизненным циклом сокета. Init отправляется не в тот момент и не на тот экземпляр сокета - соединение уже закрыто или ссылка на ws уже очищена, а логика инициализации всё ещё пытается работать как будто сокет живой.

## Анализ бага

### Текущее поведение (Дефект)

1.1 WHEN WebSocket соединение открывается И во время задержки 50ms для стабилизации прокси происходит событие close THEN `this.ws` устанавливается в `null` обработчиком `handleClose`, и последующая попытка отправить init сообщение завершается неудачей (`sent: false`)

1.2 WHEN init сообщение не отправляется из-за `this.ws === null` THEN сервер не получает init сообщение, handshake не завершается, и соединение остаётся в неинициализированном состоянии

1.3 WHEN обработчик `handleClose` вызывается во время выполнения асинхронного `handleOpen` THEN происходит race condition между установкой `this.ws = null` и попыткой использовать `this.ws` для отправки сообщения

### Ожидаемое поведение (Корректное)

2.1 WHEN WebSocket соединение открывается THEN обработчик `handleOpen` SHALL захватить ссылку на WebSocket instance в локальную константу до начала асинхронных операций, чтобы гарантировать работу с тем же экземпляром сокета на протяжении всего handshake

2.2 WHEN происходит задержка 50ms для стабилизации прокси THEN система SHALL использовать захваченную локальную ссылку на WebSocket для отправки init сообщения, независимо от изменений `this.ws` другими обработчиками

2.3 WHEN init сообщение отправляется через захваченную ссылку на WebSocket THEN сообщение SHALL быть успешно отправлено, если захваченный WebSocket instance находится в состоянии OPEN, даже если `this.ws` был изменён обработчиком `handleClose`

2.4 WHEN WebSocket закрывается во время выполнения `handleOpen` THEN обработчик `handleClose` SHALL корректно обработать закрытие и очистить `this.ws`, но это НЕ SHALL помешать отправке init сообщения через захваченную локальную ссылку

2.5 WHEN метод `send()` вызывается с WebSocket instance напрямую THEN метод SHALL проверять `ws.readyState === WebSocket.OPEN` для переданного instance, а не полагаться только на `this.ws`

2.6 WHEN обработчик `handleClose` проверяет, какой сокет закрылся THEN он SHALL сравнивать закрытый сокет с `this.ws` и очищать `this.ws` только если это тот же экземпляр

### Неизменяемое поведение (Предотвращение регрессии)

3.1 WHEN WebSocket соединение успешно открывается И init сообщение успешно отправляется И сервер отвечает connected сообщением THEN система SHALL CONTINUE TO переходить в состояние `connected` и запускать heartbeat мониторинг

3.2 WHEN WebSocket закрывается с кодом 1000 (нормальное закрытие) THEN система SHALL CONTINUE TO корректно обрабатывать закрытие без попыток переподключения

3.3 WHEN WebSocket закрывается с кодом 1006 после успешного handshake THEN система SHALL CONTINUE TO инициировать переподключение с экспоненциальной задержкой

3.4 WHEN задержка 50ms для стабилизации прокси выполняется THEN система SHALL CONTINUE TO ожидать указанное время перед отправкой init сообщения для корректной работы с прокси (nginx, ngrok)

3.5 WHEN обработчик `handleClose` вызывается THEN система SHALL CONTINUE TO устанавливать состояние `disconnected`, очищать `this.ws`, и вызывать пользовательские обработчики

3.6 WHEN метод `send()` вызывается с сообщением THEN система SHALL CONTINUE TO проверять `this.ws.readyState === WebSocket.OPEN` перед отправкой и возвращать `false` если соединение не активно
