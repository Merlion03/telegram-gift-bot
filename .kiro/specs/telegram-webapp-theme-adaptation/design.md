# Дизайн исправления адаптации темы Telegram WebApp

## Обзор

Форма доставки (DeliveryForm.tsx) имеет критическую проблему с видимостью текстовых элементов при использовании светлой и тёмной тем Telegram. Лейблы полей формы не видны на обеих темах, а введённый текст в инпутах плохо различим на тёмной теме из-за неправильного применения CSS переменных Telegram.

Стратегия исправления заключается в правильном использовании CSS переменных темы Telegram для обеспечения достаточного контраста между текстом и фоном во всех темах. Мы будем использовать `--tg-theme-bg-color` для фона полей ввода вместо `--tg-theme-secondary-bg-color`, и добавим fallback значения для обеспечения видимости в случае отсутствия переменных темы.

## Глоссарий

- **Bug_Condition (C)**: Условие, при котором проявляется баг - когда пользователь открывает форму в Telegram с любой темой (светлой или тёмной), и текстовые элементы (лейблы, введённый текст) имеют недостаточный контраст с фоном
- **Property (P)**: Желаемое поведение - лейблы и введённый текст должны быть отчётливо видны с достаточным контрастом на любой теме
- **Preservation**: Существующее поведение валидации, отправки формы, сообщений об ошибках и эффектов фокуса, которое должно остаться неизменным после исправления
- **DeliveryForm**: Компонент в `nextjs-app/components/webapp/DeliveryForm.tsx`, который отображает форму для ввода данных доставки
- **--tg-theme-text-color**: CSS переменная Telegram, определяющая основной цвет текста для текущей темы
- **--tg-theme-bg-color**: CSS переменная Telegram, определяющая основной цвет фона для текущей темы
- **--tg-theme-hint-color**: CSS переменная Telegram, определяющая цвет для вспомогательного текста (placeholder, подсказки)

## Детали бага

### Условие возникновения бага (Fault Condition)

Баг проявляется, когда пользователь открывает форму доставки в Telegram WebApp с любой темой (светлой или тёмной). Компонент `DeliveryForm` неправильно применяет CSS переменные темы, что приводит к недостаточному контрасту между текстом и фоном.

**Формальная спецификация:**
```
FUNCTION isBugCondition(input)
  INPUT: input of type { theme: 'light' | 'dark', element: 'label' | 'input-text' }
  OUTPUT: boolean
  
  RETURN (input.theme IN ['light', 'dark'])
         AND (input.element == 'label' AND labelNotVisible(input.theme))
         OR (input.element == 'input-text' AND input.theme == 'dark' AND inputTextNotVisible())
END FUNCTION

FUNCTION labelNotVisible(theme)
  // Лейблы используют --tg-theme-text-color, но могут сливаться с фоном
  RETURN contrast(--tg-theme-text-color, background) < 4.5
END FUNCTION

FUNCTION inputTextNotVisible()
  // Введённый текст использует --tg-theme-text-color на фоне --tg-theme-secondary-bg-color
  RETURN contrast(--tg-theme-text-color, --tg-theme-secondary-bg-color) < 4.5
END FUNCTION
```

### Примеры

- **Светлая тема, лейблы**: Пользователь открывает форму в Telegram со светлой темой → лейблы "ФИО", "Адрес доставки" не видны или плохо различимы → ожидается: лейблы отчётливо видны с тёмным текстом на светлом фоне
- **Тёмная тема, введённый текст**: Пользователь вводит "Иванов Иван" в поле ФИО на тёмной теме → текст плохо виден на тёмном фоне → ожидается: текст отчётливо виден со светлым цветом на контрастном фоне
- **Тёмная тема, лейблы**: Пользователь открывает форму в Telegram с тёмной темой → лейблы не видны → ожидается: лейблы отчётливо видны со светлым текстом на тёмном фоне
- **Placeholder текст**: Пользователь видит placeholder "Иванов Иван Иванович" → ожидается: placeholder виден, но с меньшим контрастом чем основной текст (используя `--tg-theme-hint-color`)

## Ожидаемое поведение

### Требования к сохранению (Preservation Requirements)

**Неизменное поведение:**
- Валидация полей формы должна продолжать работать корректно с теми же правилами (минимальная длина, формат телефона и т.д.)
- Отправка данных на API должна продолжать работать без изменений
- Сообщения об ошибках валидации должны продолжать отображаться красным цветом
- Стилизация и поведение кнопки отправки должны продолжать работать без изменений
- Блокировка полей ввода в состоянии отправки (isSubmitting) должна продолжать работать
- Эффекты фокуса (focus ring) должны продолжать отображаться корректно

**Область действия:**
Все входные данные, которые НЕ связаны с визуальным отображением текста и фона (цвета, контраст), должны быть полностью не затронуты этим исправлением. Это включает:
- Логику валидации формы
- Обработку отправки данных
- Взаимодействие с Telegram WebApp SDK
- Обработку ошибок и состояний загрузки
- Структуру DOM и классы элементов

## Гипотеза корневой причины

На основе анализа кода и описания бага, наиболее вероятные причины проблемы:

1. **Неправильный выбор CSS переменной для фона инпутов**: Компонент использует `--tg-theme-secondary-bg-color` для фона полей ввода, но эта переменная может иметь недостаточный контраст с `--tg-theme-text-color` на тёмной теме. Правильнее использовать `--tg-theme-bg-color`, который обеспечивает основной фон с гарантированным контрастом.

2. **Отсутствие явного контраста для лейблов**: Лейблы используют `--tg-theme-text-color`, но не имеют явного фона, что может привести к слиянию с фоном формы. Возможно, нужно добавить дополнительную стилизацию или использовать другую переменную.

3. **Недостаточные fallback значения**: Fallback значения (`#000000` для текста, `#ffffff` для фона) могут не обеспечивать достаточный контраст в некоторых случаях, особенно если переменные Telegram не загружены.

4. **Проблема с placeholder**: Placeholder текст может использовать неправильную переменную или не иметь достаточного контраста. Нужно использовать `--tg-theme-hint-color` для placeholder.

## Свойства корректности

Property 1: Fault Condition - Видимость текстовых элементов на всех темах

_Для любого_ входного состояния, где пользователь открывает форму доставки в Telegram с любой темой (светлой или тёмной), исправленный компонент DeliveryForm ДОЛЖЕН отображать лейблы полей и введённый текст с достаточным контрастом (минимум 4.5:1 по WCAG AA), обеспечивая отчётливую видимость всех текстовых элементов.

**Валидирует: Requirements 2.1, 2.2, 2.3, 2.4**

Property 2: Preservation - Сохранение функциональности формы

_Для любого_ взаимодействия пользователя с формой, которое НЕ связано с визуальным отображением цветов (валидация, отправка, обработка ошибок, фокус), исправленный компонент ДОЛЖЕН производить точно такой же результат, как и оригинальный компонент, сохраняя всю существующую функциональность валидации, отправки данных, обработки ошибок и состояний.

**Валидирует: Requirements 3.1, 3.2, 3.3, 3.4, 3.5, 3.6**

## Реализация исправления

### Необходимые изменения

Предполагая, что наш анализ корневой причины верен:

**Файл**: `nextjs-app/components/webapp/DeliveryForm.tsx`

**Компонент**: `DeliveryForm`

**Конкретные изменения**:

1. **Изменение CSS переменной для фона инпутов**: Заменить `--tg-theme-secondary-bg-color` на `--tg-theme-bg-color` для всех полей ввода (input и textarea)
   - Это обеспечит правильный контраст между текстом и фоном
   - `--tg-theme-bg-color` - основной фон, который гарантированно контрастирует с `--tg-theme-text-color`

2. **Добавление стилизации для placeholder**: Добавить CSS для placeholder текста, используя `--tg-theme-hint-color`
   - Это обеспечит видимость placeholder с меньшим контрастом чем основной текст
   - Применить через псевдоклассы `::placeholder`

3. **Улучшение fallback значений**: Обновить fallback значения для обеспечения контраста в случае отсутствия переменных Telegram
   - Для светлой темы: текст `#000000`, фон `#ffffff`
   - Для тёмной темы: текст `#ffffff`, фон `#1c1c1d` (стандартный тёмный фон iOS)

4. **Проверка контраста для лейблов**: Убедиться, что лейблы используют правильную переменную и имеют достаточный контраст
   - Лейблы должны использовать `--tg-theme-text-color` с fallback `#000000`
   - Фон формы должен быть контрастным (использовать основной фон страницы)

5. **Добавление стилей для border**: Обновить цвет border для полей ввода, используя `--tg-theme-hint-color` для лучшей видимости границ
   - Это поможет визуально отделить поля ввода от фона

## Стратегия тестирования

### Подход к валидации

Стратегия тестирования следует двухфазному подходу: сначала выявить контрпримеры, демонстрирующие баг на неисправленном коде, затем проверить, что исправление работает корректно и сохраняет существующее поведение.

### Исследовательская проверка условия бага

**Цель**: Выявить контрпримеры, демонстрирующие баг ДО реализации исправления. Подтвердить или опровергнуть анализ корневой причины. Если опровергнем, нужно будет пересмотреть гипотезу.

**План тестирования**: Написать тесты, которые симулируют открытие формы в различных темах Telegram и измеряют контраст между текстом и фоном. Запустить эти тесты на НЕИСПРАВЛЕННОМ коде, чтобы наблюдать провалы и понять корневую причину.

**Тестовые случаи**:
1. **Тест светлой темы - лейблы**: Симулировать открытие формы со светлой темой Telegram, измерить контраст лейблов с фоном (провалится на неисправленном коде - контраст < 4.5:1)
2. **Тест тёмной темы - введённый текст**: Симулировать ввод текста в поле на тёмной теме, измерить контраст текста с фоном инпута (провалится на неисправленном коде - контраст < 4.5:1)
3. **Тест тёмной темы - лейблы**: Симулировать открытие формы с тёмной темой, измерить контраст лейблов с фоном (провалится на неисправленном коде - контраст < 4.5:1)
4. **Тест placeholder**: Симулировать отображение placeholder текста, проверить использование `--tg-theme-hint-color` (может провалиться на неисправленном коде)

**Ожидаемые контрпримеры**:
- Контраст между лейблами и фоном меньше 4.5:1 на обеих темах
- Возможные причины: неправильное использование CSS переменных, отсутствие явного фона, недостаточные fallback значения

### Проверка исправления (Fix Checking)

**Цель**: Проверить, что для всех входных данных, где выполняется условие бага, исправленная функция производит ожидаемое поведение.

**Псевдокод:**
```
FOR ALL input WHERE isBugCondition(input) DO
  result := DeliveryForm_fixed(input)
  ASSERT expectedBehavior(result)
END FOR

FUNCTION expectedBehavior(result)
  // Проверка контраста для лейблов
  ASSERT contrast(result.labelColor, result.backgroundColor) >= 4.5
  
  // Проверка контраста для введённого текста
  ASSERT contrast(result.inputTextColor, result.inputBackgroundColor) >= 4.5
  
  // Проверка использования правильных CSS переменных
  ASSERT result.inputBackgroundColor == '--tg-theme-bg-color'
  ASSERT result.placeholderColor == '--tg-theme-hint-color'
  
  RETURN true
END FUNCTION
```

### Проверка сохранения (Preservation Checking)

**Цель**: Проверить, что для всех входных данных, где условие бага НЕ выполняется (функциональные взаимодействия, не связанные с цветами), исправленная функция производит тот же результат, что и оригинальная.

**Псевдокод:**
```
FOR ALL input WHERE NOT isBugCondition(input) DO
  ASSERT DeliveryForm_original(input) = DeliveryForm_fixed(input)
END FOR
```

**Подход к тестированию**: Property-based тестирование рекомендуется для проверки сохранения, потому что:
- Оно автоматически генерирует множество тестовых случаев по всему домену входных данных
- Оно выявляет граничные случаи, которые могут быть упущены в ручных unit тестах
- Оно предоставляет сильные гарантии, что поведение не изменилось для всех не-багованных входных данных

**План тестирования**: Наблюдать поведение на НЕИСПРАВЛЕННОМ коде для валидации, отправки и других взаимодействий, затем написать property-based тесты, фиксирующие это поведение.

**Тестовые случаи**:
1. **Сохранение валидации**: Наблюдать, что валидация работает корректно на неисправленном коде, затем написать тест для проверки, что она продолжает работать после исправления
2. **Сохранение отправки**: Наблюдать, что отправка данных работает на неисправленном коде, затем написать тест для проверки сохранения этого поведения
3. **Сохранение сообщений об ошибках**: Наблюдать, что ошибки отображаются красным на неисправленном коде, затем написать тест для проверки сохранения
4. **Сохранение эффектов фокуса**: Наблюдать, что focus ring отображается корректно на неисправленном коде, затем написать тест для проверки сохранения

### Unit тесты

- Тест контраста лейблов на светлой теме (минимум 4.5:1)
- Тест контраста введённого текста на тёмной теме (минимум 4.5:1)
- Тест контраста лейблов на тёмной теме (минимум 4.5:1)
- Тест использования правильных CSS переменных (`--tg-theme-bg-color`, `--tg-theme-hint-color`)
- Тест fallback значений при отсутствии переменных Telegram
- Тест валидации формы (сохранение поведения)
- Тест отправки данных (сохранение поведения)

### Property-Based тесты

- Генерация случайных тем (светлая/тёмная) и проверка контраста для всех текстовых элементов
- Генерация случайных входных данных формы и проверка сохранения валидации
- Генерация случайных состояний формы (isSubmitting, errors) и проверка сохранения поведения UI
- Тестирование на множестве сценариев, что визуальные изменения не влияют на функциональность

### Integration тесты

- Тест полного потока заполнения формы на светлой теме с проверкой видимости всех элементов
- Тест полного потока заполнения формы на тёмной теме с проверкой видимости всех элементов
- Тест переключения между темами (если поддерживается) и проверка адаптации цветов
- Тест визуальной обратной связи при фокусе на полях ввода
- Тест отображения ошибок валидации с проверкой их видимости
